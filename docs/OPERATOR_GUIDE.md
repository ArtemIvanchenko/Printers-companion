# Установка и обновления для операторов

## Один раз перед началом работы

1. На ПК должен работать Docker: Docker Desktop на Windows; Docker Desktop
   или OrbStack на Mac. Это существующая среда вычислений, отдельная служба
   обновлений, Python или Git не нужны.
2. Подключите Tailscale к той же сети, что NAS. Администратор предоставляет
   адрес NAS и реквизиты БД/файлового хранилища. Не пересылайте пароли в общий чат.
3. Скачайте установщик из [Releases](https://github.com/ArtemIvanchenko/Printers-companion/releases):
   `mac-arm64.dmg` для Mac с Apple Silicon, `mac-x64.dmg` для Intel,
   `win-x64.exe` для Windows x64. В названии тестового файла есть `-test`.
4. Установите и откройте Printer’s Companion Test. Для нового ПК заполните
   форму NAS один раз. Для существующей установки выберите «Импортировать
   существующую установку»: сохраняется её исходная папка, а не копия базы.
5. Дождитесь открытия рабочего экрана. Если запуск не завершён, прочитайте
   сообщение и используйте повторный запуск; не удаляйте `.env` или базу.

**Старый запуск через папку проекта / версия 1.7.0:** не удаляйте его и не
создавайте новый идентификатор ПК. Установка без протокола безопасного обновления
требует отдельного перехода с разработчиком: резервная копия, окончание расчётов,
сверка путей/реквизитов и схемы. Простая установка нового окна этот переход
не выполняет. Установщик блокирует небезопасное переключение.

NAS только хранит общие карточки и файлы. Приложение не устанавливается на NAS.
Задание, созданное одним ПК, выполняется на нём; второй ПК не подхватывает его.
Не выключайте ПК с незавершёнными расчётами или локальной очередью загрузки.

## Перед допуском конкретного рабочего ПК

На отдельной проверочной карточке проверьте: загрузку STL, открытие/скачивание
того же файла, завершение расчёта, импорт тестового лога и открытие отчёта.
На втором ПК проверьте чтение общей карточки. После закрытия и открытия приложения
карточка должна сохраниться. Зелёный NAS или HTTP 200 сами по себе не проверяют
этот рабочий сценарий. Не используйте для пробы оригиналы незавершённой печати.

## Как обновлять сейчас

В этом выпуске нет подписи разработчика. Кнопка «Проверить обновления» честно
сообщает, что подписанный канал выключен. Она не скачивает случайные скрипты
и не маскирует отсутствие автообновления.

После завершения загрузок и расчётов закройте окно и установите следующий
**тестовый** выпуск поверх прежнего тестового приложения. На Mac заменяется
только приложение в «Программах», на Windows повторно запускается установщик.
Операторская папка и общая БД не удаляются. Откройте программу: контейнеры
приводятся к точной версии пакета, а готовность проверяется. Если программа
сообщает об активном расчёте, дождитесь его окончания и завершите обновление.
Не запускайте второй экземпляр старой и новой программы параллельно.

Не удаляйте папку проекта, `.operator-state`, `.update-state`, `raw_logs`,
`.env.operator` или профиль приложения. Не выполняйте `docker compose down -v`,
Docker prune и переустановку NAS ради обновления.

## Что нужно разработчику для обычного автообновления

- Настроить Apple Developer ID + notarization и Windows code-signing certificate.
  Это реквизиты разработчика, не каждого оператора.
- Собрать подписанные приложения с включённым стабильным каналом, проверенным
  манифестом контейнеров и update-feed. Неподписанный выпуск не заменяет этот шаг.
- Проверить настоящее обновление A→B и восстановление на Mac/Windows, включая
  загрузку и активный расчёт. Переход с test appId на подписанное приложение
  выполняется отдельно с сохранением прежней операторской папки.
- Далее оператор нажимает «Проверить обновления» → «Обновить и перезапустить».
  Работающие расчёты ждут завершения; NAS автоматически не мигрирует.

## Порядок выпуска для разработчика

1. Обновить VERSION/desktop metadata, commit, push; дождаться зелёного CI **этого SHA**.
2. Поставить тег `vX.Y.Z` на этот commit и отправить тег.
3. Release workflow собирает/публикует контейнеры, проверяет их SHA/протокол,
   записывает immutable digests и передаёт манифест в сборки Mac ARM/Intel/Windows.
4. Только после native smoke и Docker lifecycle появляются Release, установщики
   и SHA256SUMS. Не выдавать один `git push` или tag за готовый релиз.
5. При сбое CI исправить причину и выпустить следующий номер; не заменять
   опубликованные immutable артефакты другим содержимым под прежним номером.
