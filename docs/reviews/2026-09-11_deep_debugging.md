# Глубокая отладка — 11 сентября 2026

База исходников: `c46658b`. Ниже — локальные исправления поверх опубликованной
версии. Код и локально работающие процессы проверены отдельно от сохранённых
аналитических отчётов. Операторская БД не использовалась для тестов, исходные
логи/модели не менялись, исторические карточки не переанализировались автоматически.

## Воспроизведённые проблемы и исправления

1. **Обработчик расчёта завершался при потере NAS.** Ошибка подключения во время
   получения задания происходила вне обработчика ошибок. Это подтверждено локальным
   журналом и отсутствием процесса после остановки OrbStack. Внешний цикл теперь
   повторяет попытки с задержкой 2–30 с; остановка прерывает ожидание. Восстановление
   не меняет владельца и не расходует попытки обработки входных данных. Очередь ML
   получает очередь выполнения и при постоянном потоке расчётов времени.
2. **Сбой GitHub CI на границе процессов.** В запуске `34490494887` миграции прошли,
   а subprocess-тест падал с отсутствующим `compute_node_id` в неполной тестовой
   подмене настроек. Linux/Python 3.11 наследовал её через `fork`. Подмена теперь
   содержит реальные настройки; совместимый старый пул использует явный `spawn`,
   не наследуя открытые соединения API и состояние нативных библиотек. Основной
   production-путь остаётся в долговечной очереди отдельного worker.
3. **Неполная проверка пересечений прожига.** Сравнение только соседних окон
   пропускало третий слой внутри длинного окна первого. Проход по максимальному
   правому краю исключает все конфликтующие слои; касание границ разрешено.
4. **Недостоверная попытка не исключала слой из нормального времени.** Корректная
   запись плюс `timing_valid=false` для того же слоя оставляли его в нормальном
   итоге. Теперь такой слой неоднозначен независимо от порядка файлов. Валидные
   измеренные попытки сохранены как исторические наблюдения, но не как штатный цикл.
5. **Тихая перезапись при распаковке.** `day.log`/`DAY.LOG` и Unicode-варианты одного
   имени могли обозначать один файл на Mac/Windows и разные ключи в словаре.
   Введён общий NFC/casefold-ключ, сравнение SHA и сохранение первой ссылки на
   источник. Непустой каталог отвергается; атомарная публикация не заменяет
   существующий файл. Оригинальные архивы не меняются.
6. **Ложная готовность локального запуска.** Старый прокси принимал TCP, но
   закрывал соединение при протокольной проверке PostgreSQL. Сам PostgreSQL
   напрямую отвечал. После проверки отсутствия активных задач перезапущены только
   локальные процессы прокси/API. Launcher теперь проверяет `/health/ready`, а не
   только порт и `/health`. Причина внутреннего отказа старого процесса отдельно
   не установлена; её нельзя автоматически приписать сети или самой БД.
7. **Тесты могли использовать настоящую локальную очередь файлов.** Read-only
   контейнер выявил эту зависимость ответами 507. Теперь каждый тест имеет свою
   временную NAS-outbox, harness отказывается от не-тестовой/не-SQLite БД.

Версия аналитики увеличена до `0.4.1`, диагностики — `log-insights-1.0.1`.
Старые сохранённые отчёты не становятся отчётами новой версии без перерасчёта.

## Проверки

- macOS, Python 3.14: **798 passed**, Ruff и `git diff --check` проходят.
- Внутренняя среда Docker, Python 3.11: **796 passed, 2 skipped**. Два пропуска —
  JS-проверки из-за отсутствия Node в runtime-образе; они прошли на Mac.
- Отдельный прогон subprocess/recovery: 10 тестов прошли в Docker.
- Проверка ORM против действующей PostgreSQL прошла; чистая SQLite прошла всю
  цепочку Alembic и drift-check. Единственный head — `0021_layer_cycle_models`.
- Проверка защитного отказа harness с `APP_ENV=local` намеренно завершилась до
  инициализации схемы: случайный запуск тестов на операторских настройках запрещён.
- Живой API: 97 карточек, первые две страницы по 10 без пересечений; все восемь
  карточек с логами и их `log-insights` ответили успешно. Геометрический контекст
  по всем восьми остаётся `unconfirmed_context`, а не искусственно подтверждается.
  `/health/ready` подтверждает PostgreSQL, Redis и MinIO.
- Linux не добавляется как отдельная операторская платформа. Контейнерная проверка
  нужна для среды Docker из текущих Windows-скриптов запуска. Нативный Windows
  в этой сессии не запускался.
- Первый полный контейнерный прогон выявил также `noexec` в созданной тестовой
  tmpfs: это ограничение стенда, не дефект приложения. В повторном тестовом
  контейнере `/tmp` разрешал запуск фиктивных команд теста обновления; настройки
  безопасности рабочих контейнеров не ослаблялись.
