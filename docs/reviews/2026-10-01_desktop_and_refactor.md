## Разделение источников и измеренная оптимизация

`RuntimeRepository`: **949 → 773 строки**. Raw mirror, восстановление исходников
и их проверка перенесены в `domain/services/session_sources.py`; старые методы и
aliases удалены, внутренние потребители мигрированы. Репозиторий больше не
открывает исходники и MinIO. Форматы измерений и семантика аналитики прежние;
ANALYSIS_VERSION не меняется лишь из-за ускорения эквивалентного вычисления.

- Owner проверяется до открытия исходников. Отдельный SQL snapshot копирует
  только metadata источников, затем закрывает транзакцию до локального парсинга.
  Сохранённые, в том числе пустые/отклонённые, измерения запрещают raw fallback.
- Доступный неразобранный файл сверяется по сохранённым SHA-256 и размеру.
  Изменение inode/размера/mtime во время хеширования или разбора, неизвестный
  checksum и повреждённый immutable mirror требуют повторного импорта, а не
  публикации частичного результата. Уже заполненный ParseResult не переоткрывается.
- Maintenance читает detached входы, считает вне SQL и перед записью сверяет
  заблокированную сессию. Современный анализ ремонтируется исходным ImportJob,
  не частичной заменой JSON. Legacy timing-only manifest без source сохраняет
  свои слои и не превращается в полную публикацию аналитики.
- Все варианты ZIP используют общую распаковку после сохранения raw-архива.
  SHA-манифест строится при копировании блоков; повторное чтение распакованного
  дерева удалено. Независимая проверка SHA в ingestion, CRC, лимиты и lease
  сохраняются.
- На этой промежуточной итерации PostgreSQL писал до 500 обычных событий одним
  идемпотентным запросом, SQLite
  сохраняет размер 25 из-за старого ограничения bind-параметров. Границы commit
  и fencing не укрупняются. Для 500 строк число запросов **20 → 1**; на локальном
  стенде median **121.35 → 120.61 мс**, то есть ускорение в 20 раз не измерено.
  Выигрыш здесь — меньше сетевых round trips к NAS.

executemany до 500 строк. Удалены сборка отдельного SQL-выражения для каждого

через ORM bulk-режим, который мог бы пропустить их. Сохранены last-duplicate-
wins, исходный created_at при повторе, caller flush/rollback/commit и все
authoritative проверки lease/generation вокруг записи.

Это штатная операция [SQLAlchemy Core](https://docs.sqlalchemy.org/en/20/core/connections.html)
и [psycopg executemany](https://www.psycopg.org/psycopg3/docs/advanced/pipeline.html),
без нового кеша, сериализатора, зависимости или raw-DBAPI обхода Session.
В PostgreSQL с используемым libpq драйвер передаёт отдельные операции pipeline-
пакетом; это **не один SQL statement на 500 строк** и не обещание одного
сетевого round trip. Для SQLite каждый statement имеет 19 bind-параметров,
так что прежний предел 999 не умножается на размер пакета.

Изолированный PostgreSQL, Python 3.14.6, SQLAlchemy 2.0.50, psycopg 3.3.4
binary/libpq 18; 500 настоящих canonical rows мартовской сессии, только

  оказался медленнее parameter batch (**41,327 мс**) и не внедрён.
- Три серии по 20 пакетов с неизменёнными границами rollback: median wall
  **2 381,762 → 499,922 мс**, CPU локального процесса **1 974,408 → 252,795 мс**.
  CPU PostgreSQL backend через /proc/stat: median **39 → 36 ticks**.
  В этом локальном опыте рост CPU сервера не обнаружен; это не измерение
  слабого удалённого NAS, его сети, WAL/fsync или полной нагрузки контейнера.
- Отдельный PostgreSQL контракт на 1 002 входах/1 001 уникальной строке:
  все поля совпали со старым путём, NULL/defaults/Unicode/последний дубликат и

### Привязка аномалий без повторного расчёта общей геометрии

## Дневная итерация: нарезчик, штриховка и пути поддержек

Завершена 01.10.2026 около 15:35 по Москве; к ночному запуску до 10:00

### Два устранённых источника лишней работы

1. **Штриховка.** PySLM создавал линии на большую охватывающую область и
   отправлял в точный Clipper все линии, включая заведомо не пересекающие
   ни один контур. `_clip_hatch_lines` выполняет только консервативный
   segment/box отбор по X, Y и нормали отрезка. Box расширен на две единицы
   сетки Clipper; арифметика отбора float64, а исходные координаты, pseudo-Z
   IDs и порядок оставшихся линий не изменяются. Точное пересечение остаётся
   в `BaseHatcher.clipLines`, прежние угол, шаг, offset, отверстия и точность
   не меняются. Использована штатная точка расширения Hatcher, не patch
   установленной библиотеки.
2. **Сборка путей поддержек.** Профиль одного сечения STL с 432 449 гранями:
   около 5,77 с, из них 4,81 с в graph traversals; SciPy повторно проверял и
   преобразовывал один COO-граф для 3 744 обходов. `_section_path` строит
   тот же Path2D, но CSR float64 готовит один раз на сечение. Оставлены
   штатные `mesh_multiplane`, `tol_path.merge_digits`, unique-порядок вершин,
   leaf-first undirected DFS, `fill_traversals`, последовательность сущностей,
   `to_3D` и `face_index`. Ни одну линию/петлю не заменяли оболочкой, не
   меняли merge tolerance или правила open/closed. Есть MIT attribution в
   `docs/THIRD_PARTY_NOTICES.md`; глобальных patches и новых кешей нет.

Дополнительно исправлен реальный contour-only случай: PySLM представлял
отсутствие пересечений как массив `(1, 0, 2)`, затем Hatcher обращался к
несуществующим endpoints. Теперь это настоящий пустой массив `(0, 2, 3)`.
Маленькая деталь с контуром, но без внутренней штриховки, остаётся сканируемой,
а не падает/отбрасывается. Старые успешные результаты сохраняют семантику;
из этого исправления не следует право менять старые снимки или их версии.
