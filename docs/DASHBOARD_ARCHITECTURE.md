# Архитектура дашборда

Документ описывает целевую структуру интерфейса и причины решений. Написан
после того, как накопилось 16 плоских экранов и навигация перестала читаться.

Техническое состояние после рефакторинга 23 сентября 2026: GET `/` отдаёт
HTML-оболочку без SQL; CSS и сценарии находятся в `web_assets/dashboard/`.
Chart/Three/шрифты поставляются локально с SHA-256 manifest и лицензиями.
История загружается при открытии через ограниченные read models; полные массивы
телеметрии читаются только для выбранной сессии. Каталог — по 10 карточек,
«Ещё» добавляет следующие 10. Classic globals/inline handlers пока сохранены.
0 SQL относится к HTML, не ко всем последующим API-запросам браузера.

## Кто и зачем пользуется

Дашборд **аналитический**, не операционный (в терминологии NN/G). Два главных
сценария, названные владельцем:

1. **Посчитать время и цену будущей печати** — пришли STL/STEP, надо ответить
   заказчику.
2. **Разобрать прошедшую печать** — что пошло не так, какая была атмосфера,
   насколько прогноз сошёлся с фактом.

Мониторинг «что со станком прямо сейчас» — НЕ главный сценарий. Поэтому статус
станка занимает одну строку, а не половину главного экрана.

## Две сущности и почему их нельзя схлопнуть

- **Карточка печати** — что печатаем: модели, материал, толщина слоя, фото,
  документы, прогноз времени и себестоимости.
- **Сессия логов** — как прошло: длительность, слои, телеметрия, аномалии.

Их **нельзя объединить в одну автосоздаваемую сущность**: карточка заводится в
момент получения файлов от заказчика, а реальная печать может случиться через
несколько дней. Автопривязка по дате в такой ситуации ненадёжна.

Привязка остаётся ручной — задача интерфейса не убрать её, а сделать заметной:
**сессия без карточки это незавершённая работа**, и она должна попадаться на
глаза, а не лежать в отдельной вкладке, куда надо догадаться зайти.

## Текущая структура

```
ПЕЧАТИ ───────────── карточки и фильтры: без логов, без оценки, с аномалиями
  └ [печать] ─────── вкладки одной печати:
                       · Что печатали — модели, материал, фото, документы
                       · Прогноз — время, себестоимость, разбивка
                       · Как прошло — машинное время, паузы, слои
                       · Процесс — телеметрия и аномалии этой печати
                       · Файлы — STL/Magics/логи
ДОБАВИТЬ ПЕЧАТЬ ───── папка целиком → распознавание → новая/существующая карточка
ОЦЕНКА ВРЕМЕНИ ────── последний прогноз и подтверждённая точность «оценка/факт»
АНОМАЛИИ ──────────── очередь наблюдений по всем печатям и вердикт оператора
КАЧЕСТВО ──────────── подтверждённые исходы и состояние модели риска
ЖУРНАЛ ────────────── операторские записи о газе, порошке и обслуживании
ПАРАМЕТРЫ ─────────── параметры машины и калибровочные коэффициенты
```

Было 16 технических равноправных экранов. Теперь верхний уровень показывает
семь ежедневных сценариев из утверждённого дизайн-макета, а технические разрезы
одной печати остаются внутри её карточки.

**Что изменилось принципиально:** «Телеметрия», «Качество», «История», «Тренды»
больше не являются одинаковыми техническими страницами. Телеметрия и файлы —
**разрезы одной печати**. Глобальные «Аномалии» и «Качество» — очереди работы по
всем печатям; из них оператор переходит к конкретной карточке и доказательствам.

## Принципы, на которых это построено

| Принцип | Источник | Следствие |
|---|---|---|
| Обзор → зум → детали | Шнайдерман, «The Eyes Have It» (1996) | В печать проваливаются из списка |
| Один экран, 5–9 метрик | Стивен Фью, «Information Dashboard Design» | «Печати» — рабочий каталог, а не свалка графиков |
| Аналитический ≠ операционный | NN/G | Статус станка ужат до строки |
| Иерархия вместо плоскости | GoodData, принципы ИА дашбордов | Служебное убрано под шестерёнку |

## Раскладка «Печатей»

Важное — слева-сверху (F-паттерн сканирования).

```
┌──────────────────────────────────────────────────────────┐
│  ПЕЧАТИ · N       [Все][Без логов][Без оценки][Аномалии] │
├──────────────────────────────────────────────────────────┤
│  ⚠ непривязанные логи / незавершённая карточка           │
├────────────────────┬────────────────────┬────────────────┤
│  STL-превью        │  STL-превью        │  + ДОБАВИТЬ    │
│  имя, дата, статус │  имя, дата, статус │    ПЕЧАТЬ      │
│  время, слои, риск │  время, слои, риск │                │
└────────────────────────┴─────────────────────────────────┘
```

Пустые статкарты вроде `Газ 0 бар` и `Порошок 0.0 кг` не занимают верх экрана.
Главная показывает карточки, настоящий STL и только те предупреждения, по
которым оператор может выполнить действие.

## Исторические наблюдения при проектировании

Ниже — старый снимок данных, не текущая диагностика базы. Перед исправлением
операторской базы требуется новая read-only проверка. В исходном снимке:

- **Материал не пишется принтером в логи вообще** (проверено grep по всем
  реальным логам). Задаётся только оператором — решено: один раз в карточке
  печати, наследуется всем расчётам этой печати. Без него нет ни
  себестоимости, ни калибровки по материалам.
- **Привязок карточка↔сессия было ноль**, `/prints` был пуст — поэтому блок
  «точность прогноза» пустой.
- **Имя печати отсутствует**: в списке сессий выводится `session_20260411_a8d31dad`
  и рядом та же дата второй колонкой. Человеку нужно имя заказа/детали.

## Состояние данных на момент написания

Разбор реальной БД (11 «печатей») показал, что настоящих печатей 4. Остальное:
5 дублей от импорта до фикса группировки и 3 записи, заведённые из скриншота и
`.DS_Store`. Починено в коде (см. коммиты по session_grouping и runtime repo),
чистка самой БД — отдельным решением.

Наблюдения этого снимка, требующие независимой проверки, а не автокоррекции:

- `SO2 = 19.2%` требует проверки привязки канала, единиц и датчика;
  сама запись не доказывает причину или действительный кислород в камере.
- `SF1 = 0` — зарегистрирован ноль; отсутствие физического потока без
  подтверждения схемы канала и работоспособности датчика не доказано.
- Сессия 23.03 показывает 99 часов и пересекается по времени с сессией 27.03 —
  похоже на накрутку суток при переходе через полночь.
