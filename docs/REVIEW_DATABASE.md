# Ревью работы с базой данных

Замеры сделаны на живой БД проекта (Postgres 16.14, 12 МБ, 11 сессий).

## Короткий ответ на три вопроса

1. **Postgres — правильный выбор, менять не нужно.** И не потому, что «данных много»
   (их мало), а именно из-за требования общего доступа: SQLite не умеет
   конкурентную запись по сети, и любая сетевая ФС ломает его блокировки.
2. **В PostgreSQL записываются агрегаты, а не весь временной ряд.** В карточке
   хранятся статистики и до 150 точек-превью из ~81 000 строк. Полный исходный
   пакет логов до разбора обязательно архивируется в MinIO на NAS.
3. **NAS — хранилище, а не вычислительный узел.** PostgreSQL и MinIO общие, но
   парсинг, расчёт времени и ML выполняет ПК, создавший задание. `time_log`
   дополнительно зеркалируется как быстрый вход калибровки; это не очередь
   для других ПК и не даёт им права перехватить чужой расчёт.

|---|---|

Остальные 40 пусты. Это не «мало данных» — часть таблиц не используется
принципиально: данные, которые они должны хранить, лежат в JSON.

**Мёртвый код репозиториев** (0 обращений вне самих файлов):
`EventRepository`, `QualityRepository`, `InsightsRepository` — 203 строки.
Живые: `RuntimeRepository` (154 обращения), `PrintsRepository` (41).

### Данные лежат в JSON, а не в схеме

`canonical_events`, `source_files`, `state_transitions`, `segments` — пусты,
хотя события и файлы у сессий есть: всё это внутри `sessions.context`
(JSON до 56 КБ на сессию).

Следствия:
- SQL-запрос «покажи все сессии, где был аларм по кислороду» написать нельзя —
  придётся вытащить и распарсить JSON всех сессий в Python;
- индексов по содержимому JSON нет (GIN не создан), фильтрация — только полным
  перебором;
- денормализованные колонки разъезжаются с payload. Пример, уже исправленный в
  этой сессии: `sessions.classification` никогда не записывался и у всех 11
  сессий содержал дефолт, пока payload говорил `REAL_PRINT`.

**Это не значит, что надо всё нормализовать.** При 11 сессиях JSON проще и
работает. Но стоит понимать цену: любой новый вопрос к данным требует кода, а не
запроса.

### Индексы

132 индекса, создаются миграцией — здесь всё в порядке.

Исходно `sessions.classification` не был индексирован, хотя участвует в
фильтрации. Миграция `0010_index_session_classification` добавила
`ix_sessions_classification`; этот пункт закрыт.

## 2. Что стоило бы записывать, но не записывается

### Полная телеметрия

`_MAX_TELEMETRY_POINTS = 150` (`domain/services/session_overview.py:35`).
В БД попадает 150 точек, в исходном `sensors.log` — 81 378 строк.

Агрегаты (`signal_stats`: mean/std/p95/alarm_count по 18 сигналам) считаются по
полному файлу и сохраняются — это правильно. Сам ряд не лежит в PostgreSQL,
но не теряется: он остаётся в raw-архиве MinIO. Для нового графика или статистики
его нужно явно восстановить на владеющем ПК и запустить локальный пересчёт.

### Сырые логи

Перед парсингом исходный пакет архивируется в `raw-logs` на NAS. Обычный
файл или папка сохраняются пофайлово с SHA-256 в ключе; ZIP хранится как
один неизменный исходный архив. Если MinIO не принял пакет, production-импорт не
начинает анализ и повторяется позже.

`time_log` после разбора дополнительно копируется под ключом сессии. Это маленький
быстрый индекс для калибровок, а не единственная копия сырых данных.

### Что теряется при потере файлов

Функции с `rehydrate=True` сначала ищут локальный рабочий файл, а `time_log` могут
получить из быстрого зеркала MinIO. Полный raw-пакет долговечен, но его
произвольные семейства пока не подключены к автоматическому rehydrate. Для нового
анализа полной телеметрии нужен явный локальный запуск восстановления/пересчёта:

| Место | Что перестанет работать | На чужой машине |
|---|---|---|
| `scan_calibration.session_burn_by_layer` | модель времени скана не обучится | работает (зеркало `time_log`) |
| `recoat_calibration.session_recoat_seconds` | калибровка нанесения слоя | работает (зеркало `time_log`) |
| `recoat_calibration.session_machine_seconds_by_layer` | машинное время как «факт» | работает (зеркало `time_log`) |
| `api/routes/sessions.py` | повторная генерация отчёта из всех семейств | сохранённый отчёт виден всем; для нового разбора нужно явно восстановить raw-пакет на владеющем ПК |

## 3. Целевая топология NAS

Инфраструктура уже подготовлена (`deploy/nas/`): Postgres + MinIO на Synology
через Tailscale. Каждый операторский ПК выполняет только собственные задания,
закреплённые по `owner_node_id`; NAS хранит PostgreSQL/MinIO и ничего не
вычисляет. Локальных production-баз в этом режиме нет: все читают единый
PostgreSQL, а интерфейсы инвалидируют кэш через локальный SSE fan-out.

Поток одной печати устроен так:

1. Локальный API записывает карточку и задание с `owner_node_id` этого ПК.
2. Модели и логи потоково записываются в MinIO. Логи не анализируются,
   пока полный raw-пакет не записан на NAS.
3. Локальные `worker` и `estimator` выбирают только задания своего
   `COMPUTE_NODE_ID`, выполняют парсинг, геометрию и ML на этом ПК.
4. Готовые снапшоты попадают в PostgreSQL и видны всем операторам.

Другой ПК читает уже сохранённый результат и не подхватывает фоновую работу.
Если владеющий ПК выключен, задание ждёт его возвращения. Переназначение может
быть только отдельным явным административным действием, а не failover-механизмом.

Карточки, привязки, параметры машины и калибровочные коэффициенты общие сразу.
Компактное зеркало `time_log` закрывает пути калибровки. Остаточное ограничение:
для повторного разбора всех семейств логов raw-архив нужно явно восстановить на
владеющем ПК. Монтировать общую NAS-шару как `RAW_LOGS_HOST_PATH` на всех ПК не нужно.
