# Заметки для агентов, работающих над этим репозиторием

Этот проект ведётся одним человеком в связке с ИИ-агентами — иногда несколько
агентов работают параллельно, на разных машинах, в разных сессиях. Этот файл —
общая память между ними: не инструкции "что делать", а контекст и история
решений, чтобы не наступать повторно на одни и те же грабли и не откатывать
то, что уже было сознательно исправлено.

Обновляйте этот файл, когда узнаёте что-то важное для следующего агента —
не только читайте.

---

## Параллельная работа нескольких агентов

Пользователь одновременно взаимодействует минимум с двумя ИИ-агентами над
этим репозиторием — один в этой сессии, другой на отдельном Windows-ПК
(наблюдался использующим модель "DeepSeek V4 Flash" через инструмент вида
OpenCode/Zen). Это уже приводило к реальным конфликтам:

- Локальный git-клон на одной машине может сильно отставать от `origin/main`
  даже при чистом `git status` — см. раздел ниже про переписанную историю.
- Агенты независимо строили конфликтующие механизмы (см. историю
  автообновления) — один в одну сторону, другой в противоположную,
  одновременно.

**Перед тем как считать что-то «актуальным» — всегда `git fetch origin` и
сравнение с `origin/main`**, а не просто проверка `git status`. Чистое
рабочее дерево означает только отсутствие незакоммиченных изменений, но
ничего не говорит о том, насколько сама локальная ветка устарела.

## История: переписанная история main

В какой-то момент `origin/main` был переписан (force-push, вероятно
rebase/squash) — ранние коммиты похожи по содержанию, но имеют другие хэши.
Локальный клон, сделанный до этого момента, не имеет общего предка с новым
`origin/main` (`git merge-base` ничего не находит), из-за чего `gh pr create`
может упасть с "no history in common". Если это случится снова — не паниковать
и не форсить: проверить, что содержимое локальных коммитов действительно
присутствует в `origin/main` (по содержимому, не по хэшам), и только затем
делать `git reset --hard origin/main` на локальной `main`.

## Автообновление — единственный механизм, не добавлять параллельный

**Текущий дизайн (сознательное решение, не забывать):** обновление происходит
**только** по клику на иконку на рабочем столе. Никакого фонового опроса,
никакой службы, никакой кнопки в дашборде, которая что-то запускает.

Поток: иконка → `deploy/launch.ps1` → проверяет Docker → `deploy/update.ps1`
(git pull + `docker compose up -d`) → ждёт `/health` → открывает дашборд.
`deploy/launchers/Запустить.bat` / `Запустить.command` — самодостаточные
варианты для установки с нуля, тоже проверяют обновления при каждом запуске.

**Убрано намеренно и не должно возвращаться:**
- Задача Task Scheduler (`PrintersCompanionUpdater`) — опрашивала флаг-файл
  каждую минуту в фоне, независимо от иконки.
- launchd-агент на macOS — реагировал на флаг-файл мгновенно, в обход иконки.
- `POST /admin/update` в API — писал этот флаг-файл. Контейнер физически не
  может выполнить обновление сам (нет доступа к Docker), так что этот
  эндпоинт был нужен только для фонового механизма выше.
- Кнопка «Обновить» и весь связанный UI в дашборде — дёргали этот эндпоинт.
  Осталась только пассивная информация (есть ли новая версия на GitHub, без
  единого действия).

Если увидите, что кто-то пытается вернуть фоновую проверку обновлений или
кнопку в дашборде — это, скорее всего, шаг назад, а не вперёд. Спросите
пользователя, прежде чем это делать.

(Более раннее решение — Watchtower — было убрано ещё раньше, до этого пункта
разработки, и вообще не должно упоминаться нигде в актуальном коде.)

## Миграция на общий NAS (Synology DS224+, через Tailscale)

Цель: несколько операторских ПК сейчас имеют каждый свою локальную БД
(Postgres) и хранилище (MinIO) — карточка печати с одного ПК не видна на
других. План — вынести Postgres + MinIO на один общий Synology DS224+, чтобы
все ПК читали/писали одни и те же данные.

NAS физически стоит не в той же локальной сети, что рабочие ПК (у начальника
дома) — обычный LAN-файрвол не подходит. Выбран **Tailscale** (WireGuard
mesh VPN) — да, Tailscale официально заблокирован для российских IP с конца
2024, и это было явно обсуждено с пользователем; решение подтверждено
осознанно ("тэилскэйл работает"), пересматривать без повода не нужно.

Готово, но не задеплоено (нет доступа к NAS): `deploy/nas/docker-compose.yml`
(Postgres+MinIO), `deploy/nas/.env.nas.example`,
`deploy/nas/docker-compose.client-remote-db.yml` (клиентский оверрайд),
`deploy/nas/README.md` (полный runbook). Решение: переносить БД начали с
чистого листа, без миграции старых локальных данных — значит после подъёма
Postgres на NAS обязательно нужно прогнать `alembic upgrade head`, прежде чем
клиенты начнут к нему подключаться.

## Вкладка «Тестовые метрики»

Вкладка дашборда (Настройки → 🧪 Тестовые метрики,
`analytics/test_metrics/ml_showcase.py` + `api/routes/test_metrics.py`)
прогоняет пять внешних ML/статистических библиотек на реальных сигналах
сессии: **ruptures** (точки смены поведения ST5), **PyOD** IsolationForest
(совместные аномальные окна по SO1/ST5/SP4), **tsfresh** (автопризнаки по
SO1), **LightGBM + SHAP** (прогноз + объяснение по SO1), **River**
(потоковое обнаружение аномалий по Flow T). Чисто экспериментальный слой, в
основной pipeline алармов не встроен.

Выбор библиотек согласован с уже существующими зависимостями проекта, не
взят с нуля:
- **LightGBM, не XGBoost** — проект уже использует lightgbm в
  `analytics/prediction/defect_risk.py`.
- **ruptures уже был зависимостью** — используется в `analytics/cross_session.py`
  для сравнения между сессиями. Здесь другое применение (внутри одной сессии,
  по сырому сигналу) — не дублирование.

Все пять библиотек работают на **полном разрешении данных**, без
даунсэмплинга — ранний вариант урезал всё до 120k строк ради скорости, но
это рискует незаметно потерять короткие всплески датчиков. Единственное
исключение — **River** (чистый Python-цикл, ~24 сек на файле 1.28М строк) —
у него есть защитный потолок в 2 млн строк, который не срабатывает ни на
одном реальном файле проекта.

Побочная находка при проверке на реальных логах (`~/Desktop/Логи`): датчик
`Flow T` периодически выдаёт огромные мусорные значения (например,
`7.9×10³⁴`) — встречается в 8 из 19 реальных файлов сессий. Похоже на
системную проблему датчика/электроники, стоит показать инженеру принтера.

## Известные грабли при локальной сборке

- `.env.secrets` отсутствовал в `.dockerignore` (в отличие от `.env`) —
  секреты попадали в слой образа. Ни один текущий сервис в
  `docker-compose.yml` не использует `.env.secrets` в рантайме (сервиса
  `telegram-bot` больше нет, `TELEGRAM_BOT_TOKEN_HASH` берётся из `.env`).
  Исправлено (см. `.dockerignore`).
- `pydantic-settings` (`core/config/settings.py`) сам читает `.env` и
  `.env.secrets` с диска при старте **каждого** сервиса (api/worker/
  watcher/scheduler) — независимо от механизма `env_file:` в
  docker-compose.yml. Если у `.env.secrets` на хосте слишком строгие права
  (например 600 у другого владельца) — при копировании в образ (COPY
  сохраняет права) непривилегированный пользователь контейнера не сможет
  его прочитать, и сервис упадёт при старте с `PermissionError`.
- `watcher` требует существования папки `${RAW_LOGS_HOST_PATH}/incoming` на
  хосте (см. `INCOMING_PATH` в `.env`) — иначе `watchdog` падает с
  `FileNotFoundError` при старте и уходит в restart-loop.
- `DATABASE_URL` обязательно должен быть `postgresql+psycopg://...`, не
  голый `postgresql://` — иначе SQLAlchemy пытается использовать psycopg2,
  которого нет в образе. Это ловится как жёсткая ошибка в
  `core/preflight.py::check_database_url` при любом `APP_ENV`.
- `REDIS_URL` внутри Docker-сети должен указывать на `redis://redis:6379/0`
  (имя сервиса), не `localhost` — иначе контейнер стучится сам в себя.

## Найдено на реальных логах (`~/Desktop/Логи`): многодневные печати режутся по сессиям — НЕ ПОЧИНЕНО

Принтер ротирует **все** семейства логов (`_time.log`, `_burn.log`, `_sensors.log`,
`_stateFlow.log`, главный `.log`) по календарным суткам **независимо от того, идёт
печать или нет** — это не «один набор файлов на печать», как предполагалось при
правке группировки сессий (`domain/services/session_grouping.py`, PR #21, ключ —
общий префикс имени файла). Печать, переходящая через полночь, получает
**разные префиксы на разные календарные дни** и у `group_files_into_sessions`
никогда даже не сравнивается между собой — разъезжается на несколько неполных
сессий.

Подтверждено на двух реальных случаях по номерам слоёв в `_time.log`
(`layer_timing_summary`, поле `layer`):
- `27.05.2026_time.log`: слои 2..384 → `28.05.2026_time.log`: слои 384..950
  (последний слой дня N = первый слой дня N+1).
- `08.06.2026_time.log`: слои 2..1133 → `09.06.2026_time.log`: слои 1134..1983.

Рабочий сигнал для склейки через границу дня уже есть в данных — непрерывность
номера слоя между последним событием файла дня N и первым файла дня N+1. Не
реализовано: `group_files_into_sessions` сейчас не знает о таком случае вообще.

Побочная находка того же расследования: суммарное активное время по слоям
(`burn_ms + pour_ms` из `time_log`) для многодневной печати 27.05→29.05 дало
только ~29.5 ч, а по меткам времени в главном логе между первым и последним
событием прошло ~47.6 ч настенных часов — то есть **~18 ч простоя/пауз** нигде
не учитываются ни в `plate_estimator`, ни в `recoat_calibration` (PR #22, #23).
Это отдельный, полностью немоделируемый по геометрии компонент времени печати.

Статус: найдено и подтверждено на реальных данных, **не исправлено** — ждёт
решения пользователя, с чего начинать (склейка сессий vs учёт пауз).

Отдельно подтверждено на тех же логах: реальная медиана `pour_ms` (нанесение
слоя) держится ~9.25 с по всем материалам/толщинам слоя — близко к
`_DEFAULT_RECOAT_MS=9500`. Значит калибровка `recoat_time_by_mat` (PR #23)
работает корректно, но на обычных однодневных печатях цифры заметно не
сдвинет — константа и так была почти верной.

## Точность прогноза времени печати: архитектура после Level B

Хронология решений (чтобы не откатывать сознательное):

1. **Слагаемые времени печати разделены и калибруются независимо**:
   скан (burn) + нанесение (pour/recoat) + паузы (не моделируются вообще —
   отдельная задача). Реальные послойные значения обоих слагаемых пишет сам
   принтер в `*_time.log` (`layer_timing_summary`: `burn_ms`, `pour_ms`).
2. **Нанесение**: `recoat_time_by_mat` (миграция 0007) — медиана реальных
   `pour_ms`. По реальным логам медиана стабильна ~9.25 с при любых режимах,
   т.е. старая константа 9500 мс была почти верна. Оставлено ради честности
   источника, не ради сдвига цифр.
3. **Скан**: единый послойный движок `layer_engine.py` — ВСЕ тела плиты
   (детали+поддержки) совместно хэтчатся PySLM на общей оси Z
   (`Hatcher.hatch()` принимает произвольные пути, не только STL). Удалены как
   неточные: усреднение 10 сечений × слои (`_pyslm_layer_metrics`) и
   безперескоковая эвристика поддержек (`_section_scan_hours`).
   Грабли, найденные при этом: (а) `to_2D()` у trimesh даёт каждому телу СВОЙ
   2D-фрейм — полигоны разных тел нельзя объединять/мерить без обратной
   трансформации в глобальный XY (`_to_plate_xy`); (б) пересекающиеся контуры
   (поддержки проникают в деталь) при хэтчинге гасятся even-odd — нужен
   `unary_union` полигонов уровня.
4. **Калибровка скана** (`scan_calibration.py`, миграция 0008): NNLS-регрессия
   реального `burn_ms` слоя на геометрию того же слоя. Два жёстких вывода из
   валидации на реальных печатях: коэффициенты — НЕ физические скорости
   (коллинеарность; никогда не показывать 1/beta как скорость), и модель НЕ
   переносится между режимами (0.06→0.025 дал R²<0) — ключ строго
   `материал@толщина`, на чужой режим — паспортная физика.
5. **Цифры валидации** (продакшн-модули, реальные печати): физика по пресетам
   −54%/−89%; подогнанная модель: сумма −0.0%/+0.6% in-sample, блочная CV
   → ожидание ~±10% (края ±25%) на будущей печати того же режима.
6. Геометрия слоёв сохраняется в снапшот прогноза (`scan_geometry`), чтобы
   калибровка не переслайсивала плиту и была устойчива к багу многодневных
   логов (частичные слои — валидные точки).
7. **Принцип «без пауз» — обязательный, применяется на ОБЕИХ сторонах любой
   калибровки, не только к прогнозу.** Прогноз всегда был чистым машинным
   временем (скан+нанесение); но факт для `accuracy.py`
   (`prediction_accuracy`/`recalibrate_and_apply`) исходно брался как
   настенный интервал сессии (`end_ts - start_ts`) — заражённый паузами.
   Это молча тянуло паузы в одеяльный `time_correction_by_mat`: печать с
   долгой паузой выглядела как «печать с заниженным прогнозом» и раздувала
   коэффициент для ВСЕХ печатей материала. Исправлено: факт теперь —
   Σ(burn_ms+pour_ms) из `time_log` сессии
   (`recoat_calibration.session_machine_seconds_by_layer`,
   `accuracy._machine_hours_from_logs`), настенный интервал — только
   запасной путь, если лога нет. Пойман по дороге острый край: без проверки
   покрытия слоёв частичный лог (суточная ротация, см. п.6/находку про
   многодневные сессии выше) даёт ЗАНИЖЕННУЮ сумму, которую наивно спутать с
   «фактом» — обязательна проверка `len(per_layer) >= 0.95 * expected_layers`
   (и отдельный минимум-слоёв-этаж на случай отсутствующего
   `expected_layers` в старых/битых снапшотах — иначе 2-слойный обрывок лога
   пройдёт как «весь факт печати»).
   ГЛАВНЫЙ путь снижения отклонения прогноза — накопление статистики:
   каждая новая привязанная печать режима с логами добавляет данные в NNLS
   (п.4) автоматически при `/prints/recalibrate` — ничего вручную включать
   не нужно, только печатать и привязывать сессию к карточке.

## Как пользователь любит работать

- Ведёт разработку один, но "один" значит "один + ИИ-агент" ("разработку я
  веду один с тобой") — не профессиональный разработчик по бэкграунду,
  задаёт базовые концептуальные вопросы ("зачем вообще нужен Docker?",
  "не критично ли терять такой объём данных?") — объяснять простым языком,
  без лишнего жаргона. При этом быстро схватывает, ловит реальные
  несостыковки в том, что ему говорят, и жёстко указывает, если что-то не
  сходится с тем, что было согласовано раньше.
- Не открывать и не мёржить PR без отдельного явного разрешения каждый раз
  ("и пр и мерж", "да, мёржи") — пуш ветки делать можно проактивно, а вот
  создание PR и тем более merge — только по прямому запросу.
- Если пишете инструкцию, которую пользователь перешлёт нетехническому
  человеку (начальнику, оператору) — по умолчанию делайте её подробной и
  структурированной: пронумерованные шаги, короткое "зачем" под каждым
  крупным шагом, точные названия кнопок/пунктов меню как в реальном
  интерфейсе, и финальный чек-лист "что прислать в ответ".
- Иногда присылает фото монитора принтера (не скриншот) в `.HEIC` — файл
  нужно сконвертировать (`sips -s format jpeg ...`) перед тем, как читать.
