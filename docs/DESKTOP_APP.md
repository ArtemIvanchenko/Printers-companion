# Настольный Printer's Companion

## Контракт

Одна установленная программа для macOS и Windows, без отдельной службы
обновлений. Основной процесс окна управляет **только локальным** Docker.
Аналитика остаётся в контейнерах; PostgreSQL и MinIO — на NAS.
Окно существующего дашборда не получает Docker socket, shell или произвольный IPC.

## Порядок реализации и приёмки

1. Готовый host runtime внутри установщика, без Git/Python на ПК оператора.
2. Постоянные данные в userData вне .app/Program Files; импорт существующего
   проекта оставляет .env, очереди, mounts, volumes и compute-node на месте.
3. Единственный экземпляр окна и один lifecycle: startup/readiness, безопасная
   остановка, восстановление. NAS-схема автоматически не мигрирует.
4. Настольное окно: первый запуск/настройка, текущий интерфейс, встроенные
   действия обновления. IPC только из доверенного главного frame.
5. Стандартное обновление **настольного пакета**, затем приведение контейнеров
   к версии из манифеста установленного пакета. Старый backend хранится для
   восстановления. Нельзя объявлять обновление завершённым при разных версиях.
6. Установщики macOS Intel/ARM и Windows x64; native-host тесты и smoke-проверка.
7. Подписанный публичный выпуск — только после настройки сертификатов,
   успешного контейнерного CI данного SHA и проверки реальных целевых ПК.

Сертификатов пока нет: локальные артефакты являются **тестовыми**, не подписанным
релизом. Без них автоустановка публичного обновления на macOS не считается
проверенной. Тесты с имитацией Docker не доказывают реальный запуск/расчёт.

## Постоянное состояние

Новая установка хранится в `app.getPath('userData')/operator`. Манифест и
Compose-ресурсы входят в пакет программы; секреты и журналы находятся только в
операторской папке. Привязка существующего проекта хранит его исходный абсолютный
путь: перенос БД, очередь NAS и старые файлы не копируются и не удаляются.
Версия Python-host и публичные корневые TLS-сертификаты включены в сборку через
PyInstaller; Python/OpenSSL/Homebrew на операторском ПК не требуются. Host не скачивается при
каждом запуске. Терминальные скрипты остаются совместимым developer-путём.

## Ограничения безопасности

- Проверять принадлежность Docker context и Compose-проекта данному ПК/папке.
- Обновлять готовые versioned-образы, сверять полный SHA/версию/source_state.
- Сохранять durable journal до переключения; сначала скачивание/проверки.
- Расчёты ждут завершения; новые запросы закрывает локальный maintenance gate.
- Не использовать `down -v`, prune, произвольные remote Docker context или
  автоматические миграции общей базы.
- Удалённая/вложенная страница не управляет host runtime через IPC.
- Файлы/секреты не включаются в Docker context, установщик, диагностический вывод.

## Запуск, переключение и восстановление

Обычное открытие окна возвращает сохранённый backend: уже работающий контейнер
не пересоздаётся из-за другого Compose hash/tag. Проверяются фактический image ID,
ключевые env и mounts; остановленный контейнер запускается по его ID. Создание
действительно отсутствующего compute-сервиса не запускает новое хранилище NAS.

До установки native-пакета host выполняет `prepare-restart`: закрывает новые
записи, завершает принятые HTTP-загрузки/публикации outbox, проверяет локальные
running jobs, приостанавливает только свободных потребителей и повторяет проверку.
Здесь контейнеры ещё не убиваются и версия не меняется. Состояние `restart_ready`
записано на диск; отмена или следующий запуск снимает свой gate и возобновляет
старую версию. Недостаточно просто закрыть renderer посреди upload.

После перезапуска пакет выбирает ровно свои full SHA/digests. При активном
расчёте возвращается проверенный старый dashboard с предупреждением, а повтор
планируется самим открытым окном (не отдельной службой). После переключения
проверяются весь compose app-состав, API identity и `/health/ready`.
Неуспешная проверка возвращает старые образы. Неуспешное восстановление — ошибка
с сохраняемым журналом, не зелёный статус.

Сохранённый Compose JSON экранирует `$` как `$$` для повторного чтения; сравнение
фактических env/mounts декодирует этот уровень ровно один раз. Создаваемый dotenv
отдельно экранирует `$`, кавычки и обратные слеши. Это проверяется настоящим
Compose CLI **без запуска Docker daemon**, включая кириллицу и Windows-пути.

## Воспроизводимая тестовая сборка

Из корня репозитория, с Python для текущей ОС и установленным Node.js 22:

```bash
python -m pip install -r desktop/requirements-build.txt
cd desktop
npm ci
npm test
npm run resources -- --development
npm run host
node scripts/smoke-host.cjs
npm run dist:mac -- --arm64
```

Для Intel Mac используется `--x64` и Python x64. На Windows x64 последняя
команда — `npm run dist:win`, host также собирается на Windows. Frozen binary
от другой ОС не подходит. Если Python в виртуальном окружении, задайте
`COMPANION_BUILD_PYTHON` его абсолютным путём перед `npm run host`.

`dist:mac` сохраняет DMG/ZIP в `desktop/dist`; при shell-special символах в пути
исходников .app собирается в новой безопасной временной папке (её путь печатается
после сборки). Проект пользователя не переименовывается. Команды тестовой сборки
не публикуют релиз или update feed.

Тестовый installer сохраняет отдельный appId/userData. Подписи Developer ID /
Authenticode пока нет; macOS/Windows могут предупредить о неизвестном разработчике.
Нельзя просить отключить защиту системы глобально. Unsigned channel не скачивает
и не устанавливает публичное обновление автоматически, даже если remote feed
доступен. Но по явной кнопке он действительно проверяет GitHub и предлагает
подходящий опубликованный DMG/EXE; запуск установщика остаётся ручным.

## Проверка опубликованного обновления без нового сервиса

`check-release` — read-only action существующего короткоживущего host. Он
проверяет bundled manifest, опубликованный stable tag и его точный full SHA,
затем выбирает uploaded native asset нужной ОС/архитектуры. ZIP с исходниками,
другая архитектура, неоднозначный installer и `target_commitish=main` не
подменяют установщик. Test asset должен соответствовать SHA тега и существующему
формату test-версии; это ещё не криптографическое подтверждение издателя.

Команда не создаёт operator root, не читает `.env`/installation binding, не
запускает Docker и не обращается к NAS. TLS проверяет имя хоста и сертификат;
системное доверие дополняется bundled certifi, а не отключается. Размер ответа
ограничен 2 MiB, HTTP timeout — 15 s; всё read-only child ограничено 120 s.
При зависании завершается только этот собственный проверочный процесс.

Main frame выбирает и открывает фиксированный GitHub URL сам; dashboard iframe
не получает IPC, а renderer не может передать произвольный URL установщика.
Приватный unsigned gate остаётся выключенным. `updateReady` относится только
к штатной проверенной native-загрузке; `manualUpdateAvailable` — только к ссылке
на installer. Оба не означают, что вычислительная часть уже переключилась.
Новых постоянных процессов, службы обновлений и polling-демона нет.

## Как допустить полноценное развёртывание

1. Сохранить изменения в проверенный commit; VERSION, полный Git SHA и CI
   должны относиться к этому же состоянию исходников.
2. Собрать/опубликовать compute-образы данного SHA с label
   `io.printers-companion.update-protocol=1`. Предыдущий v1.7.0 ещё не имеет
   нового протокола, поэтому его нельзя выдать за новый backend.
3. Build-time `scripts/maintenance/capture_desktop_images.py` получает точные
   verified digests. Он только читает/pulls images: без запуска контейнеров,
   миграции NAS или публикации native-пакета.
4. `npm run resources -- --development --images /absolute/path/images.json`
   связывает тестовый пакет с этими образами. Без digests или с dirty source
   новая вычислительная версия не развёртывается. Канал остаётся выключенным.
   GUI заранее показывает это ограничение и не просит реквизиты NAS для
   недоступной новой установки; импорт существующего проекта остаётся возможен.
5. Проверить реальную установку/расчёт/rollback на Mac и Windows в отдельном
   стенде. Затем сертификаты + notarization позволяют включить public build.

Старый backend без write-drain-протокола нельзя безопасно автоматически
остановить. Нужен отдельный, согласованный переход на protocol 1 после завершения
работ, резервной копии и проверки схемы/путей. Установщик блокирует неизвестный
протокол; не подменяет его принудительным SIGTERM/KILL.

## Граница проверенности

На локальном ARM Mac проверяются frozen host, DMG/ZIP, реальное окно, preload/IPC,
изолированный dashboard без privileged bridge и независимость тестовой установки.
Root pytest, Node boundary tests и offline Compose checks не заменяют NAS e2e.

`.github/workflows/desktop.yml` готовит отдельные unsigned установщики и smoke
на Mac ARM, Mac Intel и Windows x64. Workflow не изменяет main и не создаёт
Release; default test-пакеты не создают публичный feed. Signed opt-in путь
описан ниже. Его наличие не означает, что удалённый CI уже выполнялся.
05.10.2026 native CI выполнен на всех трёх платформах: frozen host, установщики
и packaged IPC/window smoke прошли. Исправлены реальная Windows lock contention,
кавычки PowerShell и GPU headless Intel smoke. Это проверочные PR-пакеты без
новых опубликованных digests, а не доступный операторский Release. Порядок
выпуска и текущие ограничения — [инструкция](OPERATOR_GUIDE.md) и
[отчёт допуска](reviews/2026-10-05_operator_readiness.md).

Четыре opt-in Docker lifecycle теста из `checks/updating/test_docker_lifecycle.py`
проверяют настоящий engine только при `COMPANION_DOCKER_CHECKS=1`; fixture
заменяет transport/schema probes, поэтому даже они не доказывают полный NAS e2e.

Если daemon локально выключен, эти четыре теста пропускаются. Рабочие контейнеры,
NAS, исходные файлы и операторская БД ради тестовой сборки не запускаются и не
изменяются. 01.10.2026 daemon включён по запросу пользователя: все четыре
проверки прошли, а текущие API/worker выполнили загрузку STL, расчёт и импорт
двух реальных логов с отдельными PostgreSQL/MinIO/Redis. Подробная граница
проверки — [отчёт](reviews/2026-10-01_desktop_and_refactor.md#реальное-выполнение-после-включения-docker).
Это не установка нового native-пакета и не NAS e2e. На ARM Mac текущие готовые compute-образы остаются linux/amd64
под эмуляцией; ARM-сборка окна не делает аналитику ARM-native.

## Подготовленный подписанный канал GitHub

Это release-time путь, а не новая служба на ПК оператора. Reusable desktop
workflow принимает `signed_release`, по умолчанию `false`. Release workflow
передаёт `true` только при repository variable `COMPANION_SIGNED_RELEASE=true`.
Signed resources требуют совпавшего `vVERSION` тега, clean commit и verified
operator-images того же full SHA. PR/обычный test workflow остаётся unsigned.

Сертификаты настраивает разработчик в GitHub Secrets: `MAC_CSC_LINK` /
`MAC_CSC_KEY_PASSWORD`, `WIN_CSC_LINK` / `WIN_CSC_KEY_PASSWORD`,
`COMPANION_PUBLISHER_NAME`. Для Mac notarization простой поддержанный режим —
`APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`; существующий builder
также поддерживает уже настроенные API/keychain credentials. Они доступны
только signing step соответствующей платформы. Без нужных реквизитов builder
отказывает; unsigned fallback вместо подписанного пакета запрещён.

Builder всегда запускается с `--publish never`: он создаёт installer/feed, но
не загружает их до завершения CI. `collect-release.cjs` в последнем release job
проверяет три native manifest, общий full SHA/images, пять installers и реальные
size/SHA-512 в feeds. Разные платформенные code_fingerprint разрешены, но имена
test-installers обязаны соответствовать своему manifest. Хеши файлов считаются
streaming, без загрузки больших пакетов целиком в RAM.

Mac ARM/Intel jobs создают одинаковое имя `latest-mac.yml`; collector объединяет
оба `files[]` в четыре DMG/ZIP записи. Перезапись одним архитектурным файлом
недопустима. Windows остаётся в `latest.yml`; optional blockmaps, pinned images
и SHA256SUMS публикует только финальный release job после всей native matrix,
smoke и Docker lifecycle. Unsigned набор никогда не публикует updater feed.
Используется уже locked js-yaml из electron-updater, без новой зависимости.

Канал пока не включён/не опубликован. Фикстуры manifest/feed не имеют подписи и
проверяют только сборочный контракт. Обязательны настоящие signed A→B на Mac
ARM/Intel и Windows, сохранность operator root, отказ/rollback и готовность
точного backend. Test appId/userData и public appId различны: первый переход
выполняется отдельно через существующую привязку папки, не переносом/удалением
данных. Сертификат и одноразовая публикация нужны разработчику, не оператору.
