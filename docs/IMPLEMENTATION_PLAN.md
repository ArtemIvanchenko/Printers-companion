# Рабочий план развития

Актуальный план текущего цикла. Архитектурные инварианты и правила выполнения
описаны в корневом `AGENTS.md`.

## Функциональные этапы

### Послойная диагностика (запрос от 9 сентября 2026)

Реализованы шесть направлений: интеграл превышений среды во время прожига,
восстановление после остановки, остаток времени относительно геометрии,
сравнение подтверждённых повторов, карта участков для контроля и баланс
задержек. Новый запрос включает сравнение повторов, ранее исключённое из цикла.
Точки входа и ограничения: `docs/LOG_INSIGHTS.md`. Старые карточки требуют
повторного импорта исходников и нового снимка прогноза; наличие кода не означает,
что конкретная историческая печать уже импортирована и пересчитана.

1. **Разметка результатов печати** — реализовано; итоговая миграция и сквозная
   проверка входят в этап стабилизации.
2. **Компактный операторский отчёт** — реализовано для карточки, сессии,
   JSON/Markdown и вкладки интерфейса.
3. **Уточнение прогноза времени** — в работе: машина, материал, толщина,
   лазеры, геометрия, нанесение порошка, controller overhead и минимальный
   цикл слоя. Паузы по решению владельца в прогноз не входят.
4. **Привязка аномалий к геометрии** — в работе: слой → высота Z → активные
   геометрические области/детали с явным уровнем уверенности.
5. **Надёжная синхронизация с NAS** — реализована, проходит отдельный набор
   тестов: локальная очередь, SHA-256, атомарная публикация, идемпотентность,
   инфраструктурные повторы и защита конфликтов ПК. Ждёт общего regression-run.
6. **Версионирование результатов** — реализовано: версия приложения/аналитики,
   git SHA, версии парсеров и моделей, хеш конфигурации и fingerprint входов.
7. **Защищённое переобучение ML** — реализовано в shadow/champion-контуре:
   локальное обучение,
   champion/challenger, shadow-проверка на будущих исходах и атомарное
   продвижение только после доказанного превосходства. Ждёт данных и общего
   regression-run, а не автоматического включения.
8. **Стабилизация** — единая Alembic-миграция, узкие и полные тесты, Ruff,
   проверка migration drift и документации развёртывания.

## Этап 10. Доказательная точность времени печати

Детальный текущий план и эталонные значения находятся в
`docs/PLAN_ACCURACY.md`.

Порядок:

1. Зафиксировать SHA-lineage подтверждённых пар и не связывать остальные
   модели по одному имени/дате — сделано.
2. Разделить граничные дубли, повторные попытки и pause-like строки — сделано
   в evidence/parser слое, требуется протянуть признаки в хранение.
3. Калибровать полный нормальный цикл как
   `max(scan + recoat + base_overhead, minimum_layer_cycle)`.
4. Сделать build origin явным и не угадывать его для нативных Magics supports.
5. Ввести fingerprint компоновки и grouped cross-validation без утечки между
   повторными печатями одной плиты.
6. Прогнать production pipeline на восьми подтверждённых парах и сохранить
   воспроизводимую таблицу худших ошибок.

Пункты прежнего списка «исторический стенд проверки», «сравнение с эталонной
печатью» и «карточка здоровья оборудования» по решению владельца проекта в этот
цикл не входят.

## Этап 9. Рефакторинг после стабилизации

Рефакторинг выполняется отдельными небольшими PR/коммитами после фиксации
поведения тестами. Функциональность и API на этом этапе не меняются.

### 9.1. Зафиксировать контракты

- Добавить characterization-тесты основных маршрутов карточки печати.
- Зафиксировать JSON-схемы карточки, прогноза, вложения, задания и отчёта.
- Отделить публичные DTO/Pydantic-схемы от внутренних словарей.

Критерий: изменение формы публичного ответа невозможно без явного обновления
версии контракта и теста миграции.

### 9.2. Разделить `api/routes/prints.py`

- `PrintCardService`: создание, изменение и optimistic concurrency.
- `PrintAttachmentService`: staging, типы файлов, checksum и object storage.
- `EstimateJobService`: проверка входов и постановка локального задания.
- `PredictionService`: подготовка входов и атомарная публикация snapshot.
- `PrintLinkService`: связь карточки/сессии, перенос разметки и зависимые задачи.

Маршруты должны выполнять только валидацию HTTP, вызывать один use-case и
формировать ответ. В них не должно оставаться геометрических алгоритмов,
прямой работы с MinIO или калибровки.

### 9.3. Разделить `storage/repositories/runtime.py`

- Репозитории сессий/отчётов.
- Репозитории качества и операторского журнала.
- Репозитории инсайтов/исторического анализа.
- Общий небольшой слой сериализации и совместимых транзакционных помощников.

Критерий: сервис зависит от узкого интерфейса, а не от универсального
`RuntimeRepository`; границы транзакций остаются на уровне use-case.

### 9.4. Разделить `web_templates/dashboard.html`

- Вынести JS по областям: карточки, загрузки, качество, аналитика, отчёт.
- Вынести общие API-клиент, escaping/render helpers и состояние страницы.
- Вынести CSS-компоненты без изменения внешнего вида.

Критерий: нет глобальных функций с пересекающимися именами, HTML не содержит
бизнес-логики, проходят XSS-тесты и сценарии вкладок.

### 9.5. Устранить дублирование аналитических выборок

- Один сервис формирует хронологическую выборку реальных печатей и актуальную
  подтверждённую разметку.
- Аналитика риска, переобучение и отчёты используют один контракт признаков.
- Fingerprint набора и правила исключения определены в одном месте.

### 9.6. Критерии завершения рефакторинга

- Полный `pytest` и `ruff check .` проходят.
- `scripts/check_migration_drift.py` не находит расхождений.
- Alembic имеет один head; чистый и существующий SQLite/PostgreSQL проходят
  upgrade.
- Публичные API и сохранённые JSON обратно совместимы.
- Долгие операции по-прежнему не держат соединение с NAS.
- Производственные расчёты по-прежнему выполняются только на ПК владельца.
