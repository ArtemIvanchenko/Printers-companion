# План: поднять точность прогноза времени печати

Цель — заменить паспортную физику подогнанными по реальным логам моделями.
Всё остальное вторично: измеренная ошибка физики на реальных плитах составляет
от −73% до +302%, тогда как погрешность геометрии — 0.7%.

## Почему именно это

Измерено на трёх реальных плитах (`docs/REVIEW_PREDICTION.md`, п.1a):

| Печать | Слоёв факт / прогноз | Факт | Прогноз | Ошибка |
|---|---|---|---|---|
| 03.06 | 833 / 834 | 8.37 ч | 10.48 ч | +25% |
| 04.06 | 1982 / 1984 | 35.91 ч | 144.23 ч | +302% |
| 27–28.05 | 946 / 950 | 29.29 ч | 7.83 ч | −73% |

Слои сходятся везде — геометрия читается верно. Ошибка целиком в скорости
скана. Реальное время прожига на слой по этим печатям: 27 с, 56 с, 102 с —
вчетверо разное при одном материале и одной толщине.

Отдельно проверена достаточность сетки по высоте: начиная с 90 уровней
результат стабилен в пределах ±0.7% (на 45 уровнях уже +4.9%). Увеличивать
не нужно — это доли процента там, где рядом стоят сотни.

## Текущее состояние (замерено)

| Что | Состояние |
|---|---|
| Послойные времена в БД | **есть** — 4 сессии, 14 032 слоя |
| Карточки печатей | 5 штук, все с привязанной сессией |
| STL в карточках | **ноль файлов** |
| `scan_geometry` в снапшотах | **нет ни у одной** |
| Подогнанные модели | **нет ни одной** |

**Цепочка обрывается на геометрии.** Без STL не считается прогноз, без
прогноза нет `scan_geometry`, без него калибровке не на чем учиться.

И главное расхождение: **в базе логи за март–апрель, а геометрия на диске —
за май–июнь. Пересечения ноль.**

Даты, где есть и логи, и геометрия (ни одна не импортирована):
`19.05`, `25.05`, `26.05`, `27.05` (+`28.05` продолжение), `03.06`, `04.06`.

## Этап 1. Наполнить данными — это и есть повышение точности

### 1.1 Импортировать логи за шесть дат

Через `POST /sessions/ingest` либо папку, которую слушает watcher. При импорте
теперь автоматически сохраняются послойные времена и зеркалируется `time_log`.

Проверка: `layer_snapshots` пополнился, в списке непривязанных появились новые
печати.

**Осторожно:** `27.05` продолжается в `28.05` (подтверждено: слои 2–384, затем
384–950). Многодневная склейка **не исправлена** — это отдельная задача, а
здесь важно, что факт надо считать по обоим файлам, иначе получится −39%
вместо честных −73%.

### 1.2 Создать карточки с геометрией

Для каждой даты — карточка, в неё STL из соответствующей папки
`~/Desktop/Все печати/Модели с печати/`. Поддержки в этих папках названы
`s_*.stl` и распознаются автоматически.

Кнопка «Создать из файлов» в разделе «Печати» делает это в один шаг: имя и дату
берёт из имени файла.

### 1.3 Заполнить материал и толщину

Обязательно и вручную — принтер не пишет их в логи вообще (проверено grep по
всем реальным логам).

Толщину можно не угадывать: число слоёв в прогнозе должно совпасть с фактом из
лога. На проверенных плитах совпадение было точным (833/834, 1982/1984,
946/950), так что несовпадение означает неверную толщину.

### 1.4 Привязать сессии к карточкам

В разделе «Печати», плашка сверху. Привязка ручная — так решено, потому что
печать случается через дни после получения файлов.

### 1.5 Рассчитать прогнозы

Кнопка «Пересчитать прогноз» в карточке. Расчёт идёт в фоне (плита считается
минутами), интерфейс опрашивает результат.

Проверка: в снапшоте появился `scan_geometry`.

### 1.6 Запустить калибровку

`POST /prints/recalibrate`. Она уже вызывается автоматически при ручной
привязке сессии, но здесь нужен явный прогон.

Модель обучается на паре «геометрия слоя ↔ реальное время прожига» и
принимается, только если проходит порог: R² ≥ 0.6, либо R² ≥ 0.2 при суммарной
ошибке ≤ 5%, при минимум 150 слоях.

**Ключевое ограничение:** модель ключуется `материал@толщина` и на другой режим
не переносится (проверено: перенос с 0.06 на 0.025 давал R² < 0). Значит для
каждого сочетания материала и толщины нужна своя печать с логами.

### 1.7 Измерить результат

Повторить замер из `docs/REVIEW_PREDICTION.md` и сравнить с −73%…+302%.

Ожидание, основанное на прошлой валидации: in-sample сумма сходится до долей
процента, на будущей печати того же режима — порядка ±10%, худшие краевые
случаи ±25%.

## Этап 2. Ускорения, не влияющие на результат

Все проверены на идентичность вывода. Порядок — по отдаче.

### 2.1 `section_multiplane` вместо цикла — 2x

Замерено: 429 с → 271 с на поддержке в 432 тыс. треугольников, при **0.000%
расхождения** значений на всех уровнях.

Требует перевернуть обход в `layer_engine.compute_layer_series`: сейчас
«уровень → все тела», нужно «тело → все уровни». Складывается с уже
реализованным параллелизмом.

### 2.2 Кеш геометрии по контрольной сумме STL

Не ускоряет первый расчёт, но убирает все повторные. Сейчас смена материала
или толщины пересчитывает геометрию заново, хотя она от них не зависит —
`LayerGeometrySeries` определяется только мешами и шагом штриховки.

Ключ: контрольные суммы файлов + `hatch_distance_mm`. Хранить рядом со
снапшотом.

### 2.3 Поднять лимит CPU контейнеру

`docker-compose.yml`, `cpus: "2.0"` → 4. До параллелизма лимит ничего не
ограничивал, теперь ограничивает. На машине 8 ядер.

### 2.4 Перенести расчёт в сервис `worker`

Он уже существует и занимается импортом и калибровками. Расчёт прогноза туда
не переехал и живёт в веб-процессе, занимая его на минуты. Скорость не
изменится — изменится отзывчивость интерфейса.

## Отклонено — и почему

| Идея | Причина отказа |
|---|---|
| Упрощение мешей поддержек | **Меняет геометрию** — у упрощённой решётки другой периметр сечения. По приоритету «точность важнее» отклонено без замера |
| Переиспользовать копии деталей (`15sht`, `33sht`) | Не работает: Magics экспортирует без сшивки вершин, `split()` даёт по телу на треугольник, сам вызов стоит 31 с |
| Сечь поддержки реже деталей | Не обосновано: поддержки меняются вдоль Z **сильнее** деталей (59.6% и 54.7% против 41.9% и 49.7%) |
| Отказаться от Docker | Не даёт скорости: контейнер оказался на 13% **быстрее** хоста (6826 мс против 7846 мс) |
| Больше уровней по высоте | Не даёт точности: с 90 результат стабилен в пределах 0.7%, время растёт линейно |

## Риски

**Многодневные печати.** Склейка сессий через полночь не исправлена. Для
27–28.05 факт придётся считать вручную по двум файлам. Это искажает и
калибровку — модель получит неполный набор слоёв. Стоит исправить до этапа 1.6,
иначе часть данных будет учтена неверно.

**Мусор в базе.** Семь записей — дубли и сессия из `.DS_Store` — всё ещё лежат
(скрипт `scripts/prune_sessions.py` готов, не запускался). Они попадут в
калибровку как отдельные печати.

**Долгий расчёт.** Плита из 93 STL не досчиталась за 20 минут. Для этапа 1.5
это означает, что 6 плит считаются часами. Пункт 2.1 стоит сделать до этапа 1,
а не после.
