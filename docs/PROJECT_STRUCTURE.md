# Структура проекта

Корень содержит только точки входа сборки и развёртывания. Рабочий код и
служебные материалы разложены по назначению:

```text
analytics/              статистика, физические признаки, ML и прогнозы
api/                    HTTP/SSE/WebSocket-граница; без тяжёлых вычислений
core/                   конфигурация, безопасность, версии, блокировки
domain/
  models/               ORM-сущности по предметным областям
  services/             сценарии импорта, связывания и анализа
parsers/                реестр и парсеры семейств файлов
profiles/m350/           профиль конкретного станка, сигналы и правила
storage/                 SQL-репозитории и объектное хранилище
worker/                  локальные владельцы долгих задач своего операторского ПК
reporting/               JSON/Markdown/LLM-представления результатов
web_templates/           операторский интерфейс и демонстрационные страницы
deploy/                  запуск, NAS и резервное копирование
scripts/
  maintenance/          разовые миграции/пересчёты данных
  ...                    диагностические и эксплуатационные утилиты
docs/
  reviews/              датированные снимки ревью, не текущая документация
migrations/versions/     только последовательные изменения схемы
tests/                   структура повторяет рабочие подсистемы
```

## Направление зависимостей

```text
API / worker → domain services → analytics / parsers → repositories → models
```

- Маршрут валидирует запрос, ставит долгую работу в очередь и формирует ответ.
- Предметный сервис не должен импортировать маршрут.
- Репозиторий отвечает только за сохранение/выборку и не запускает аналитику.
- Сырой код сигнала (`SO1`, `Flow T`) остаётся стабильным ключом; русское имя
  приходит из `profiles/signal_catalog.py`.
- `BuildJob` — производственное задание печати. Фоновые вычисления хранятся в
  `BackgroundJob`; смешивать эти сущности запрещено.
- Карточки и результаты имеют один источник истины в PostgreSQL на NAS; MinIO
  хранит модели, вложения и архив логов. NAS не выполняет аналитику.
- API, watcher, worker, estimator и Redis запускаются локально на каждом ПК.
  Создавший задание ПК остаётся его владельцем; автоматический захват чужим
  worker запрещён. Связка `COMPUTE_NODE_ID` ↔ локальный `instance-id`
  регистрируется в PostgreSQL как неизменная; два физических ПК не могут
  работать под одним именем. Standalone-scheduler в NAS-режиме отключён,
  поскольку его исторические процедуры пока не фильтруют сессии по владельцу.

## Ограничение роста файлов

- Новый алгоритм — отдельный модуль в существующем тематическом пакете и
  маленький публичный контракт в `__init__.py`, если он действительно нужен.
- Не создавать файлы `utils2.py`, `helpers_new.py`, `final.py` и копии пайплайна.
- При достижении примерно 500 строк модуль разделять по ответственности, а не
  по произвольным номерам частей.
- Скрипты, которые меняют данные, живут в `scripts/maintenance/`, поддерживают
  `--dry-run` и документируют идемпотентность.

## Известный следующий рефакторинг

`web_templates/dashboard.html` и `api/routes/prints.py` всё ещё крупнее нормы.
Их следует дробить вертикально: карточки/архив/телеметрия в статические JS/CSS,
а расчёт платформы — из HTTP-маршрута в предметный сервис. Массовое перемещение
без тестового покрытия намеренно не выполняется за один релиз.
