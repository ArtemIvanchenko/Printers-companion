# NAS как единое хранилище, расчёты на ПК операторов

Целевая схема не содержит центрального вычислительного узла и не распределяет
задания между компьютерами:

```text
ПК оператора 1                         слабый NAS
┌──────────────────────────────┐      ┌─────────────────────────────┐
│ локальные API + Redis        │      │ PostgreSQL                  │
│ watcher + импорт + аналитика │◄────►│ карточки, задания, результаты│
│ estimator                    │      │                             │
└──────────────────────────────┘      │ MinIO                       │
                                      │ модели, вложения, логи       │
ПК оператора 2                         └─────────────────────────────┘
┌──────────────────────────────┐                   ▲
│ свой независимый локальный   │                   │
│ вычислительный контур        │◄──────────────────┘
└──────────────────────────────┘
```

Последовательность для одной печати:

1. Оператор открывает локальный интерфейс `http://127.0.0.1:8000` и создаёт
   карточку. Карточка записывается в общий PostgreSQL.
2. Загруженные модели и вложения сначала атомарно сохраняются в локальный
   outbox, затем `nas-sync` передаёт их в MinIO и публикует ссылку в PostgreSQL.
3. Загруженные логи сохраняются во входящую папку этого ПК, полностью
   архивируются в MinIO и только после успешной записи разбираются локальным
   `worker`.
4. Расчёт времени и аналитика выполняются на этом же ПК. Другой операторский
   ПК не должен забирать эти задания.
5. Результат записывается в общий PostgreSQL и сразу виден всем операторам.

Общая статистика может агрегировать на вызывающем операторском ПК уже
сохранённые нормализованные результаты; повторно читать и разбирать raw-логи
чужой сессии она не должна.

NAS выполняет только хранение и обычные SQL/S3-запросы. На нём нет API,
Redis, парсеров, ML, расчёта времени, фоновых workers или scheduler. Процесс
`nas-sync` также работает только на операторском ПК и выполняет лишь передачу.

## Состав файлов

- `docker-compose.yml` — только PostgreSQL и MinIO на NAS;
- `.env.nas.example` — секреты хранилищ NAS;
- `docker-compose.operator.yml` — локальный вычислительный контур каждого ПК;
- `.env.operator.example` — уникальная конфигурация одного операторского ПК.

Docker Compose на рабочих ПК должен быть версии 2.24.4 или новее: операторский
override использует `!override` для удаления зависимостей от локальных
PostgreSQL/MinIO и `!reset` для удаления унаследованного `env_file: .env`.

## 1. Подготовка NAS

1. Установить Container Manager и Tailscale, подключить NAS и все рабочие ПК к
   одной tailnet.
2. Создать каталоги:

   ```text
   /volume1/docker/printer-companion/postgres
   /volume1/docker/printer-companion/minio
   ```

3. Не пробрасывать порты в интернет. В firewall NAS разрешить TCP `5433` и
   `9000` только адресам операторских ПК в Tailscale. Консоль MinIO `9001` в
   штатной конфигурации наружу не опубликована.
4. Для слабого NAS особенно важны достаточное свободное место, RAID1,
   SMART-контроль и резервная копия. Аналитические нагрузки на NAS переносить
   нельзя.

## 2. Запуск хранилищ на NAS

На NAS по SSH или через Container Manager:

```bash
cd /volume1/docker/printer-companion
cp deploy/nas/.env.nas.example deploy/nas/.env.nas
# Заменить пароли в deploy/nas/.env.nas.
docker compose --env-file deploy/nas/.env.nas \
  -f deploy/nas/docker-compose.yml up -d
docker compose --env-file deploy/nas/.env.nas \
  -f deploy/nas/docker-compose.yml ps
```

Ожидаются ровно два контейнера: `postgres` и `minio`. Если на NAS появились
`api`, `worker`, `estimator`, `nas-sync`, `watcher`, `scheduler` или `redis`, запущен не тот
compose-файл.

Настройки PostgreSQL в compose намеренно консервативны: 128 МБ shared buffers,
4 МБ work memory и 100 соединений. На операторских ПК используются один API
process и маленький пул соединений, чтобы несколько компьютеров не исчерпали
ресурсы NAS.

## 3. Настройка каждого операторского ПК

На **каждом** ПК создать собственный env-файл:

```powershell
Copy-Item deploy\nas\.env.operator.example deploy\nas\.env.operator
```

Обязательно изменить:

- `COMPUTE_NODE_ID` — постоянное уникальное имя, например `M350-OP-01`; его
  нельзя копировать на другой ПК;
- `OPERATOR_STATE_HOST_PATH` — локальная постоянная папка физического ПК;
  дефолт `./.operator-state` можно оставить, но эту папку нельзя делать общей или
  копировать на другой компьютер;
- адрес NAS и пароли в `DATABASE_URL`/`MINIO_*`;
- `RAW_LOGS_HOST_PATH` — локальная папка логов именно этого компьютера;
- локальные `AGENT_API_TOKEN` и `API_SERVICE_TOKEN`.

Файл `.env.operator` содержит секреты, не должен попадать в Git и должен быть
доступен только администратору этого ПК.

Параметр `--env-file deploy/nas/.env.operator` используется Compose для
подстановки значений в явный блок `environment`. Операторский override намеренно
сбрасывает унаследованный от корневого compose `env_file: .env`: локальный
`.env` старой standalone-сборки не должен незаметно передавать контейнерам
старый адрес базы, пароли или новые неописанные переменные.

При первом старте в `OPERATOR_STATE_HOST_PATH` атомарно создаётся `instance-id`,
в подпапке `nas-outbox` хранится локальная очередь незавершённых передач,
а в PostgreSQL — неизменная пара `COMPUTE_NODE_ID` ↔ `instance-id`. Все локальные
вычислительные контейнеры читают один файл. Если другой ПК попытается
запуститься с тем же `COMPUTE_NODE_ID`, его API/worker/estimator/nas-sync откажутся
работать. Папку `.operator-state` нужно хранить между обновлениями контейнеров.
Замена физического ПК или утрата этого файла требует явной административной
перепривязки после проверки незавершённых заданий; не нужно подменять его
копией с другой машины.

На Linux каталог bind-mount должен быть доступен контейнерному пользователю
`10001:10001` на запись. На Docker Desktop (Windows/macOS) доступ обычно
преобразуется автоматически; для Linux проверьте владельца и права
`OPERATOR_STATE_HOST_PATH` до первого запуска.

Перед первым запуском новой версии остановить `api`, `worker`, `estimator`, `watcher`
и `scheduler` на всех ПК. Затем ровно на одном компьютере выполнить
одноразовую миграцию общей схемы:

```powershell
docker compose --profile migration `
  --env-file deploy\nas\.env.operator `
  -f docker-compose.yml `
  -f deploy\nas\docker-compose.operator.yml `
  run --rm migrate
```

Только после её успешного завершения запустить локальный контур на каждом ПК:

```powershell
docker compose --env-file deploy\nas\.env.operator `
  -f docker-compose.yml `
  -f deploy\nas\docker-compose.operator.yml `
  up -d api worker estimator watcher nas-sync redis
```

Открыть `http://127.0.0.1:8000`. Порт намеренно привязан только к localhost:
каждый оператор пользуется API и вычислительными процессами своего ПК.

Проверка состава:

```powershell
docker compose --env-file deploy\nas\.env.operator `
  -f docker-compose.yml `
  -f deploy\nas\docker-compose.operator.yml `
  ps
```

На обычном ПК должны работать `api`, `worker`, `estimator`, `watcher`, `nas-sync`, `redis`.
Локальных `postgres`, `minio` и `scheduler` быть не должно.

API не изменяет общую схему при старте: он сверяет установленную ревизию с
кодом и отказывается работать до выполнения `migrate`. Поэтому несколько API
не могут одновременно запустить одну миграцию.

## 4. Scheduler в NAS-режиме отключён

Существующий standalone-scheduler выполняет исторический анализ сразу по всем
сессиям и не знает, на каком ПК они были созданы. Поэтому в NAS-конфигурации он
принудительно отключён: иначе один выбранный компьютер считал бы данные других
операторов, что нарушает закрепление вычислений. Нужные расчёты запускаются
локальными `worker`/`estimator` при загрузке конкретной печати. Глобальные
периодические процедуры можно вернуть только после перевода самого scheduler
на строгую фильтрацию по `origin_compute_node_id` и локальные owner-очереди.

## 5. Проверка закрепления вычислений

Проверку проводить минимум с двумя ПК:

1. На ПК-1 создать карточку, загрузить модель и логи.
2. Убедиться, что расчётные процессы активны на ПК-1, а worker/estimator ПК-2
   не забрали это задание.
3. На ПК-2 временно указать `COMPUTE_NODE_ID` ПК-1, не копируя его
   `.operator-state`: второй контур должен отказаться стартовать. Вернуть его
   уникальный ID до следующих проверок.
4. Проверить появление объектов в MinIO и результатов в PostgreSQL.
5. Открыть карточку на ПК-2: данные и результаты должны быть видны, но новый
   локальный расчёт на ПК-2 запускаться не должен.
6. Одновременно открыть одну ревизию карточки на двух ПК. Сохранение устаревшей
   формы должно вернуть конфликт `409`, а не затереть свежую версию.
7. Остановить ПК-1 во время тестового расчёта. ПК-2 не должен автоматически
   подхватывать его задание; после возврата ПК-1 расчёт должен продолжиться или
   безопасно повториться там же.
8. Проверить NAS: CPU используют в основном PostgreSQL/MinIO на операции
   чтения-записи, а не парсинг, геометрия или ML.

## 6. Сеть и отказоустойчивость

- При недоступном NAS создание и изменение карточек и запись новых результатов
  временно недоступны: автоматического офлайн-слияния базы нет, поскольку оно
  создало бы конфликтующие версии технологических данных. Но вложение из уже
  открытой карточки принимается в локальный outbox: API возвращает `202`, а
  `nas-sync` автоматически публикует его после восстановления связи.
- Состояние очереди читается локально через `GET /sync/status`; подробный
  протокол и восстановление конфликтов описаны в `docs/NAS_SYNC.md`.
- Локальный Redis не является источником истины и не синхронизируется. После
  его потери долговечное состояние остаётся в PostgreSQL/MinIO.
- Чужой ПК не является failover-вычислителем. Переназначение незавершённой
  печати должно быть отдельным явным административным действием, а не
  автоматическим захватом задания.
- Истечение lease разрешает повторный захват только процессу с тем же
  `owner_node_id`; оно не превращает задание в общую очередь.

## 7. Резервное копирование

- Ежедневный логический `pg_dump`; одной копии каталога PostgreSQL недостаточно.
- Снимки/версионирование каталога MinIO и резервная копия на другой носитель.
- Ежемесячное тестовое восстановление PostgreSQL + MinIO в отдельный контур.
- Алерты NAS по SMART, заполнению диска и недоступности обоих контейнеров.
- Старые локальные базы не удалять минимум неделю после полной приёмки.

Откат до завершения приёмки: остановить NAS-mode стек на операторском ПК и
запустить прежнюю локальную конфигурацию. Не запускать одновременно локальную и
общую базы и не сливать их вручную.
