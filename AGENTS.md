# Printer's Companion — правила для агентов разработки

Этот файл является постоянным техническим контекстом проекта. Перед изменениями
прочитайте его целиком. Не превращайте его в журнал сессий: обновляйте только
устойчивые архитектурные решения, команды и проверяемые инварианты.

## Назначение

Система связывает карточку металлической 3D-печати, STL/Magics/фотографии,
машинные логи, операторский контекст и результаты контроля качества. Она
восстанавливает ход печати, оценивает качество данных и процесса, рассчитывает
время/стоимость, ищет аномалии и формирует объяснимые прогнозы.

## Главный инвариант распределённой установки

- PostgreSQL и MinIO располагаются на слабом NAS и являются только общим
  хранилищем данных/метаданных.
- Парсинг, геометрическое сечение STL, аналитика, ML, отчёты и переобучение
  выполняются на ПК операторов.
- Задания не распределяются между ПК. Карточка/сессия и тяжёлые задания
  закреплены за `origin_compute_node_id` / `owner_node_id` того ПК, на котором
  они были созданы.
- Долгое вычисление не должно держать транзакцию или соединение с NAS. Паттерн:
  коротко прочитать входы → закрыть транзакцию → считать локально → коротко и
  атомарно записать результат.
- Lease + generation являются fencing token. Просроченный worker не имеет права
  публиковать результат.
- Несколько операторских ПК могут читать общие карточки, но не должны молча
  перезаписывать результат друг друга. Используйте optimistic concurrency,
  idempotency keys, row/advisory locks и уникальные ограничения.

## Данные и файлы

- Библиотеки/примеры из exocad и DentalCAD не относятся к проекту: не импортируйте
  их как печати. Происхождение проверяйте по исходному пути/архиву, а не по форме STL.
- Удаление записей БД не означает разрешения удалять оригиналы или объекты MinIO.
  Перед массовой очисткой сохраняйте резервную копию и проверяемый список связей.
- Большие исходники и полные отчёты хранятся в MinIO; PostgreSQL содержит
  ссылки, контрольные суммы и ограниченные JSON-сводки.
- Любая загрузка должна проверяться SHA-256, быть идемпотентной и публиковаться
  атомарно. При недоступности NAS используется локальная долговечная очередь с
  повторными попытками и экспоненциальной задержкой.
- Одинаковое содержимое не загружайте повторно в одну карточку. Не полагайтесь
  только на имя файла.
- Значения в Monitor100 `|P|`/`|T|` позиционные и пока не имеют подтверждённой
  схемы полей. Храните сырой индекс и значение; не называйте ячейку толщиной,
  hatch distance или скоростью без спецификации прошивки либо сверки с
  независимо известным экспортом задания.

## Результаты контроля качества

Разметка должна сохранять как минимум: итог `годная/брак/неизвестно`, способ и
результат контроля, тип/тяжесть/место дефекта, диапазон слоёв, деталь, заметку,
вложения, автора и время. Исправления разметки должны быть аудируемыми. Только
подтверждённые и однозначно связанные с реальной печатью исходы допускаются в ML.

## Аналитика и ML

- Рабочие детерминированные/робастные алгоритмы, теневые модели и тестовые
  эксперименты должны быть явно разделены.
- Теневая модель не создаёт тревоги, не меняет карточку и не останавливает печать.
- Новая defect-risk модель проходит: минимальный объём и оба класса → временную
  cross-validation → регистрацию как `shadow` → проверку на будущих, не виденных
  при обучении исходах → сравнение с активной моделью/эвристикой → атомарное
  повышение до `active`. Без доказанного превосходства остаётся эвристика.
- Нельзя показывать in-sample оценку как подтверждение качества модели.
- Обучение выполняется локальным worker; NAS хранит только компактный артефакт,
  метрики и статус champion/challenger.
- Любой вывод оператору должен содержать источник (`calculated`, `calibrated`,
  `model`, `heuristic`), качество/ограничения, размер выборки и понятное объяснение.

## Версионирование и воспроизводимость

Каждый сохраняемый отчёт, прогноз и ML-артефакт должен нести:

- версию приложения и аналитики;
- git SHA сборки, если доступен;
- версии парсеров/профиля/правил, где применимо;
- хеш конфигурации расчёта;
- fingerprint входных файлов/признаков;
- идентификатор и версию применённой модели;
- ПК, выполнивший расчёт, и время.

Общие функции provenance находятся в `core/versioning/provenance.py`.

## Прогноз времени и геометрия

- Учитывайте конкретную машину/пресет, материал, толщину слоя, hatch distance,
  число лазеров, скорости/переходы, геометрию слоя, фактическое время нанесения
  порошка, нормальную межфазную задержку и заданное машиной минимальное время
  цикла слоя.
- Целевой прогноз — непрерывное нормальное машинное время. Операторские паузы,
  аварийные остановки и повторные попытки слоя в него не добавляются. Их можно
  показывать только как диагностику уже состоявшейся печати.
- Не смешивайте нормальный машинный цикл с wall-clock длительностью. В
  `*_time.log`: `burn_ms` — прожиг, `pour_ms` — нанесение порошка,
  `make_layer_ms` — полный фактический цикл; из остатка
  `make_layer-burn-pour` нужно робастно исключать pause-like выбросы. На M350
  наблюдается нижняя граница цикла: корректная модель имеет вид
  `max(burn + pour + base_overhead, minimum_layer_cycle)`, а не просто
  постоянную прибавку на слой.
- Калибровка привязана минимум к материалу и толщине слоя; не переносите модель
  между несовместимыми режимами.
- Одинаковая геометрия, напечатанная повторно, является полезным повторным
  измерением, но все её повторы должны попадать в один holdout-блок при
  cross-validation. Иначе оценка точности получает утечку.
- Аномалию слоя связывайте с высотой Z и реально активной геометрией/деталями;
  если размещение/ориентация неизвестны, явно помечайте вывод как приближённый.
- Не угадывайте начало координат построения. Если нативные поддержки Magics не
  декодированы, `Z=0` и `min Z` являются разными гипотезами. Используйте явно
  сохранённый `build_origin_z_mm`; без него показывайте диапазон/предупреждение,
  а не молча добавляйте или отбрасывайте пустые слои.
- Фото MasterSLM 2.0.6.033 и STL рукоятки с 160 282 гранями независимо
  подтвердили для одной сохранённой компоновки: `min Z=3`, `max Z=193`, слой
  0,060 мм и показанные слайсером 3 217 слоёв соответствуют
  `ceil((max Z - build_origin_z)/thickness)` при `build_origin_z=0`, а не высоте
  самого тела. Не переносите это начало координат на другой проект без его
  экспорта или операторского подтверждения.

## Импорт слайсера M350

- `PrepareModel` / `MasterSLM` сохраняют параметры в SQL-структурах
  `Projects`, `Models`, `Presets`, `HatchsStructure`, `EquidistantsStructure`,
  `SupportsStructure` и `ConesStructure`. Наличие имени поля в EXE не
  доказывает его единицу, шкалу, бинарный offset или порядок применения.
- Не принимайте неизвестный экспорт PrepareModel по расширению: пока не
  подтверждены сигнатура и сериализация, неизвестный `.data` / `.3data` /
  `.contours` / `.3dvector` / `.vi` / `.paths` должен быть сохранён как
  непрочитанный источник с SHA-256, а не интерпретирован как набор float.
- `.magics` — брендированный ZIP (`MT` вместо `PK`); перед извлечением
  проверяйте сигнатуру и CRC. Вершины печатных тел — int32 LE в 0.0001 mm.
  Нативные `SupportSurfaces_*` не являются обычным мешем: без экспортированных
  `s_*.stl` оценка времени — нижняя граница.
- `*_time.log` — подтверждённый источник реальных `pour_ms`, `burn_ms` и
  `make_layer_ms` на слой. Проверяйте `OLD_STATS` по абсолютным `NEW_STATS`.
  Полный цикл может включать pause-like выбросы: для нормального прогноза
  выделяйте штатный overhead и minimum-layer-cycle, не усредняйте wall-clock.
- Дату Magics/проекта и дату лога нельзя использовать как доказательство пары.
  Нужен сильный независимый признак (подтверждённый fingerprint, число слоёв
  или явная загрузка из карточки).

## Сопоставление карточки и логов

- Совпадение даты только создаёт список кандидатов и не доказывает пару.
- Для автоматической связи требуется независимый сильный признак: явная
  загрузка логов из карточки, согласованное число слоёв либо подтверждённый
  fingerprint компоновки; неоднозначность оставляется оператору.
- Нельзя выбирать пару по совпадению фактического времени с текущим прогнозом:
  это круговая утечка, которая затем ложно улучшит метрику этой же модели.
- Границы ежедневных/возобновлённых логов с одинаковой записью слоя считаются
  один раз. Материально отличающийся повтор того же номера — отдельная попытка,
  но этот слой исключается из калибровки нормального прожига.
- Сверка `OLD_STATS`/`NEW_STATS` привязана к соседним записям одной попытки,
  а не к порядковому номеру записи внутри слоя. `timing_valid=false` запрещает
  использовать summary в калибровке. Единый отбор находится в
  `analytics/prediction/timing_validation.py`; применяйте его сразу ко всем
  суточным файлам сессии, до фильтрации отдельных значений по диапазону.
- Дата имени сенсорного файла — дата открытия записи. Один файл может
  продолжаться несколько суток (`18.07.2026_sensors.log` до 21 июля).
  Сначала восстанавливайте все переходы через полночь, затем ограничивайте
  интервал и прореживайте график. Не приклеивайте дату имени ко всем строкам.
- При дыре ровно в один граничный слой продолжение можно склеить только по
  независимой физической непрерывности позиции стола и шага слоя. Реальный
  пример 17→18.07: основной лог содержит слой 299 в `-62690`, следующий начинает
  слой 301 в `-62810` при шаге 60; строки времени 299/300 отсутствуют и не
  считаются измеренными.

## Слайсер M350

- На исследованной поставке MasterSLM/PrepareModel параметры проекта и стратегий
  читаются из Microsoft SQL Server. Локальный `policy.db` содержит только
  настройки видимости интерфейса; не принимайте его за базу режимов.
- Подтверждённые статическим анализом сущности: `Projects`, `Models`,
  `EquidistantsStructure`, `HatchsStructure`, `SupportsStructure`. Для расчёта
  нужен их версионированный read-only экспорт без секретов.
- `settings.db` поставки может содержать привилегированные реквизиты SQL Server
  открытым текстом. Никогда не переносите их в код, отчёты или логи; используйте
  отдельную учётную запись только на чтение и ротацию обнаруженного секрета.

## Миграции и схема

- Alembic — единственный источник истины production-схемы. `create_all()` только
  для тестового harness.
- Новая миграция продолжает единственную цепочку из текущего head. Не создавайте
  параллельные heads.
- В NAS-режиме миграция запускается один раз отдельным сервисом `migrate`; API и
  worker выполняют только `assert_schema_at_head()`.
- Миграции должны работать и на PostgreSQL, и на SQLite, если нет явно
  задокументированного исключения.

## Основные точки входа

- API: `api/main.py`, маршруты в `api/routes/`.
- Импорт логов: `worker/tasks.py`, `domain/services/ingestion.py`, `parsers/`.
- Тяжёлый расчёт времени: `worker/estimate_tasks.py`,
  `analytics/prediction/plate_estimator.py`.
- Безопасное переобучение: `worker/model_tasks.py`,
  `analytics/prediction/retraining.py`, реестр в
  `storage/repositories/model_registry.py`.
- Отчёт: `reporting/json_report/generator.py`.
- Общая БД: `domain/models/`, `storage/repositories/`, `migrations/versions/`.
- NAS deployment: `deploy/nas/`.
- Послойная диагностика: `analytics/log_insights/`; поток исходных сенсоров,
  воздействие среды, восстановление, баланс времени, сравнение повторов и карта
  контроля. Порог профиля предварительный, пока явно не подтверждён оператором.
  Не интерполируйте длинные пропуски и не превращайте неизвестный остаток в паузу.
- Карточка диагностики: `domain/services/log_insights.py`,
  `GET /analysis/prints/{record_id}/log-insights`, `web_assets/log-insights.js`.
  NAS читается коротко; сравнение выполняется после закрытия транзакции.

## Работа с репозиторием

- Сохраняйте чужие незакоммиченные изменения; не используйте destructive git
  commands без явного запроса.
- Для поиска используйте `rg` / `rg --files`, для точечных правок — `apply_patch`.
- Поддерживайте обратную совместимость API и сохранённых JSON, если изменение не
  сопровождается миграцией/явной версией контракта.
- Публичные операторские названия и выводы — на понятном русском; внутренние
  идентификаторы могут оставаться английскими.

## Операторский интерфейс

- Основной визуальный язык — тёплая тёмная производственная панель без теней:
  фиксированная боковая навигация, терракотовый акцент, моноширинные подписи к
  данным и русские названия действий/показателей.
- Домашняя страница строится вокруг карточек печатей и настоящего STL-превью;
  агрегированные графики не должны вытеснять текущую работу оператора.
- Каждый рабочий экран обязан иметь состояния загрузки, отсутствия данных и
  ошибки. Данные берутся из API; демонстрационные числа нельзя выдавать за факт.
- На экране аномалий отделяйте наблюдение от причины. Частота совпадений в
  похожих печатях — контекст, а не доказательство причинности.
- Кнопки загрузки из карточки всегда прикрепляют файлы к открытой карточке, а
  не создают новую. Переключатели ракурса STL должны реально менять камеру.
- Целевая структура интерфейса и порядок выноса монолитного JavaScript описаны
  в `docs/DASHBOARD_ARCHITECTURE.md` и `docs/IMPLEMENTATION_PLAN.md`.

## Приоритетный технический долг

Наиболее нуждается в разделении `api/routes/prints.py`: сейчас там смешаны HTTP,
карточки, вложения, MinIO, очереди, геометрия, прогноз, калибровка и отчёты.
Следующий структурный этап — вынести use-case сервисы карточек/вложений,
постановки заданий и подготовки/публикации прогноза, оставив маршруты тонкими.
Следом разделить широкий `storage/repositories/runtime.py` и вынести JavaScript
из монолитного `web_templates/dashboard.html` по функциональным модулям.
Подробный порядок и критерии находятся в `docs/IMPLEMENTATION_PLAN.md`, этап 9.

## Проверка перед завершением

### Локальный просмотр на macOS / OrbStack

- `scripts/maintenance/desktop_runtime.py start` запускает текущий checkout с
  существующим локальным хранилищем; API доступен только на `127.0.0.1:8000`.
  Запускайте через `.venv/bin/python`. Это не конфигурация NAS.
- Долговечные манифесты импорта Desktop находятся в
  `.operator-state/desktop-import/`; не удаляйте их как временные файлы.
- Инструкция локального запуска и границы архивного сопоставления:
  `docs/reviews/2026-09-10_desktop_import.md`.
- `desktop_runtime.py start` запускает также отдельные процессы импорта и
  расчёта времени. Это разные очереди; одного `worker.tasks` недостаточно.
  Локальные блокировки `worker.lock` / `estimate-worker.lock` исключают повторный
  запуск процессов через этот launcher.
- Переносимые папки описываются `print-bundle.json`, версия 1. Корень каталога
  нельзя импортировать как одну печать. `model_reference` означает деталь внутри
  общей плиты: её ZIP относится ко всей печати. Контракт — `docs/IMPORT_BUNDLES.md`.
- Тесты на хосте запускайте с отдельной файловой SQLite БД через `DATABASE_URL`;
  контейнерное имя `postgres` из `.env` на хосте не подходит. Не запускайте
  интеграционные тесты на операторской БД.

Минимум:

```bash
pytest -q
ruff check .
python scripts/check_migration_drift.py
```

Для затронутого модуля сначала запускайте узкие тесты. Для миграций дополнительно
проверьте upgrade на чистой SQLite БД и отсутствие нескольких Alembic heads.
