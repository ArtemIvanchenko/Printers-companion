# Printer's Companion — правила для агентов разработки

Этот файл является постоянным техническим контекстом проекта. Перед изменениями
прочитайте его целиком. Не превращайте его в журнал сессий: обновляйте только
устойчивые архитектурные решения, команды и проверяемые инварианты.

## Назначение

Система связывает карточку металлической 3D-печати, STL/Magics/фотографии,
машинные логи, операторский контекст и результаты контроля качества. Она
восстанавливает ход печати, оценивает качество данных и процесса, рассчитывает
время/стоимость, ищет аномалии и формирует объяснимые прогнозы.

## Главный инвариант распределённой установки

- PostgreSQL и MinIO располагаются на слабом NAS и являются только общим
  хранилищем данных/метаданных.
- Парсинг, геометрическое сечение STL, аналитика, ML, отчёты и переобучение
  выполняются на ПК операторов.
- Задания не распределяются между ПК. Карточка/сессия и тяжёлые задания
  закреплены за `origin_compute_node_id` / `owner_node_id` того ПК, на котором
  они были созданы.
- Долгое вычисление не должно держать транзакцию или соединение с NAS. Паттерн:
  коротко прочитать входы → закрыть транзакцию → считать локально → коротко и
  атомарно записать результат.
- Lease + generation являются fencing token. Просроченный worker не имеет права
  публиковать результат.
- Несколько операторских ПК могут читать общие карточки, но не должны молча
  перезаписывать результат друг друга. Используйте optimistic concurrency,
  idempotency keys, row/advisory locks и уникальные ограничения.

## Данные и файлы

- Библиотеки/примеры из exocad и DentalCAD не относятся к проекту: не импортируйте
  их как печати. Происхождение проверяйте по исходному пути/архиву, а не по форме STL.
- Удаление записей БД не означает разрешения удалять оригиналы или объекты MinIO.
  Перед массовой очисткой сохраняйте резервную копию и проверяемый список связей.
- Большие исходники и полные отчёты хранятся в MinIO; PostgreSQL содержит
  ссылки, контрольные суммы и ограниченные JSON-сводки.
- Любая загрузка должна проверяться SHA-256, быть идемпотентной и публиковаться
  атомарно. При недоступности NAS используется локальная долговечная очередь с
  повторными попытками и экспоненциальной задержкой.
- Одинаковое содержимое не загружайте повторно в одну карточку. Не полагайтесь
  только на имя файла.
- Значения в Monitor100 `|P|`/`|T|` позиционные и пока не имеют подтверждённой
  схемы полей. Храните сырой индекс и значение; не называйте ячейку толщиной,
  hatch distance или скоростью без спецификации прошивки либо сверки с
  независимо известным экспортом задания.

## Результаты контроля качества

Разметка должна сохранять как минимум: итог `годная/брак/неизвестно`, способ и
результат контроля, тип/тяжесть/место дефекта, диапазон слоёв, деталь, заметку,
вложения, автора и время. Исправления разметки должны быть аудируемыми. Только
подтверждённые и однозначно связанные с реальной печатью исходы допускаются в ML.

## Аналитика и ML

- `domain/services/session_analysis.py` готовит единую интерпретацию событий,
  классификацию, признаки и provenance; `session_overview.py` и JSON-отчёт
  используют этот результат, не запускают независимый повторный анализ.
  `analysis_snapshot` schema v1 — общий компактный снимок фактов для отчёта,
  карточки и риска. Публикация проверяет полное совпадение снимков; чтение
  нового отчёта с другим снимком возвращает конфликт, не смешивает поколения.
- `session_telemetry.py` читает доступные суточные sensor-источники до прореживания.
  Health, статистика и soft sensors получают полный локальный поток; график —
  отдельную ограниченную проекцию. Отсутствующий исходник, неразобранное время
  или перекрытие отмечаются в `telemetry_evidence`; bounded parser fallback
  не объявляется полным потоком. Полнота доступных файлов не доказывает полноту
  выгрузки с принтера. Большие массивы в PostgreSQL не сохраняются.
- `idle_seconds/min/pct` больше не выводятся из wall-clock минус burn+pour.
  Есть отдельные `explicit_pause_seconds`, `unattributed_elapsed_seconds` и
  нормальный измеренный цикл. Остаток не является доказательством паузы.
- `session_overview.compute_session_spans` одним проходом исходных событий
  считает отдельно окно печати и окно слоёв. Monitor100 исключается из обоих;
  только ts_start переходов расширяет окно печати. Это elapsed-диагностика,
  не normal-cycle факт. Разные окна нельзя сливать ради сокращения обходов.
- После смены семантики признаков обновляется `ANALYSIS_VERSION` и fingerprint
  схемы модели. Старые снимки исключены из нового обучения; новая модель не
  применяется к старым признакам. Старый active-артефакт остаётся в реестре,
  но не используется новой аналитикой. Требуется повторный анализ исходников,
  а не изменение версии в сохранённом JSON вручную.
- Рабочие детерминированные/робастные алгоритмы, теневые модели и тестовые
  эксперименты должны быть явно разделены.
- Теневая модель не создаёт тревоги, не меняет карточку и не останавливает печать.
- Дополнительные экспериментальные алгоритмы не входят в обязательный импорт.
  `POST /background-analysis/shadow/{session_id}` ставит owner-local
  `shadow_analysis`; `worker/shadow_tasks.py` запускает отдельный spawn-процесс
  с лимитом `SHADOW_ANALYSIS_TIMEOUT_SECONDS`, затем сверяет входы и lease.
  Результат хранится только в задании. Текущий эксперимент использует сохранённую
  выборку графика и измеренные времена слоёв; это явно ограниченный preview,
  не полноразмерная диагностика и не замена подтверждённого defect-risk ML.
  Статусы заглушек daily review/history не означают работающее расписание.
- Новая defect-risk модель проходит: минимальный объём и оба класса → временную
  cross-validation → регистрацию как `shadow` → проверку на будущих, не виденных
  при обучении исходах → сравнение с активной моделью/эвристикой → атомарное
  повышение до `active`. Без доказанного превосходства остаётся эвристика.
- Нельзя показывать in-sample оценку как подтверждение качества модели.
- Для shadow-проверки «сессии не было в train» недостаточно: начало печати и
  серверное время регистрации её подтверждённого исхода должны быть позже
  регистрации кандидата. Исторический backfill допускается в новое обучение,
  но не в будущую проверку старого кандидата. Проверка не использует сессии,
  вошедшие в обучение действующей модели-соперника. Отсутствующее время не
  заменяется текущей датой. Правило — `analytics/prediction/retraining.py`.
- Обучение выполняется локальным worker; NAS хранит только компактный артефакт,
  метрики и статус champion/challenger.
- Любой вывод оператору должен содержать источник (`calculated`, `calibrated`,
  `model`, `heuristic`), качество/ограничения, размер выборки и понятное объяснение.

## Версионирование и воспроизводимость

Каждый сохраняемый отчёт, прогноз и ML-артефакт должен нести:

- версию приложения и аналитики;
- git SHA сборки, если доступен;
- версии парсеров/профиля/правил, где применимо;
- хеш конфигурации расчёта;
- fingerprint входных файлов/признаков;
- идентификатор и версию применённой модели;
- ПК, выполнивший расчёт, и время.

Общие функции provenance находятся в `core/versioning/provenance.py`.

## Прогноз времени и геометрия

- Учитывайте конкретную машину/пресет, материал, толщину слоя, hatch distance,
  число лазеров, скорости/переходы, геометрию слоя, фактическое время нанесения
  порошка, нормальную межфазную задержку и заданное машиной минимальное время
  цикла слоя.
- Целевой прогноз — непрерывное нормальное машинное время. Операторские паузы,
  аварийные остановки и повторные попытки слоя в него не добавляются. Их можно
  показывать только как диагностику уже состоявшейся печати.
- Согласованность OLD/NEW означает достоверность записанного счётчика, а не
  нормальность процесса. Длительная остановка может находиться внутри `pour`
  или `burn`, не только в `make-burn-pour`. Общие предварительные диапазоны
  допуска фаз находятся в `timing_validation.py`; выход за них не доказывает
  причину и не удаляет факт из диагностики. Нормальная сумма при исключениях
  относится только к допустимым измеренным слоям, а не ко всей печати.
- Не смешивайте нормальный машинный цикл с wall-clock длительностью. В
  `*_time.log`: `burn_ms` — прожиг, `pour_ms` — нанесение порошка,
  `make_layer_ms` — полный фактический цикл; из остатка
  `make_layer-burn-pour` нужно робастно исключать pause-like выбросы. На M350
  наблюдается нижняя граница цикла: корректная модель имеет вид
  `max(burn + pour + base_overhead, minimum_layer_cycle)`, а не просто
  постоянную прибавку на слой.
- `LayerGeometrySeries.at_layers` интерполирует все физические центры слоёв
  пакетно; `at_heights` принимает точные высоты выбранных строк в их порядке,
  не выводит datum и не заполняет пропущенные слои. `at(z)` сохраняется для
  отдельной точки. Диагностика остатка и подготовка scan-fit используют
  пакетную интерполяцию, но сохраняют свои разные границы допуска по Z.
  Physics/fitted пользуются одной проекцией, а minimum-cycle применяется к
  каждому слою до суммирования,
  не к интегрированным geometry totals. Заведомо неактивные Z-сечения можно
  пропускать с граничным допуском и позиционными нулями body_boundary.
- `layer_engine.py` также владеет чистыми послойными расчётами physics/fitted
  прожига и normal cycle; `plate_estimator.py` выбирает допустимые входы/модели
  и собирает результат. Общая скорость перескока по умолчанию находится в ядре,
  диагностика не импортирует private-настройки оценщика. Перенос функций не
  меняет формулы, область калибровки или fingerprint данных.
- Возврат готового XY-полигона без преобразования допустим только при точном
  совпадении первых двух строк фактической матрицы с XY identity. Нормаль
  плоскости, малая величина смещения или ожидаемый datum этого не доказывают;
  даже малые реальные смещения/повороты преобразуются, внутренние кольца
  сохраняются.
- Перед PySLM clipping разрешён только консервативный отбор линий по
  пересечению отрезка с XY-box каждого контура. Box расширяется на две единицы
  сетки Clipper; арифметика отбора float64, исходные координаты, pseudo-Z IDs
  и порядок оставшихся линий не меняются. Точное пересечение по-прежнему
  выполняет штатный clipper с прежней точностью, отверстиями и offset-путями.
  Разбиение clipping на пакеты с последующей сортировкой не эквивалентно:
  порядок векторов определяет перескоки. Пустой hatch не отменяет реальные
  контуры маленькой детали и должен быть настоящим пустым массивом, не
  фиктивным вектором; contour-only геометрия является сканируемой.
- `_section_path` собирает путь из штатного `mesh_multiplane`: тот же
  `tol_path.merge_digits`, порядок unique-вершин, leaf-first undirected DFS,
  `fill_traversals`, сущности и `to_3D/face_index`. CSR float64 готовится один
  раз на сечение, не повторно для каждой связной компоненты. Нельзя менять
  directed, порядок соседей, замыкание, классификацию open/closed или обходить
  поддержку построением её оболочки. Нет глобальных patches библиотеки или
  отдельного legacy-алгоритма; заимствованный код отмечен в third-party notices.
- `section_track_metrics_by_height` использует тот же конструктор путей для
  ограниченных multiplane-пакетов. Учитываются все Line entities, включая
  открытые ветви, которые `Path2D.discrete` может пропустить; замкнутая поддержка
  не превращается автоматически в заполненную деталь. Перескоки между сущностями
  относятся только к порядку STL-сечения: это не восстановленные команды
  принтера и не граница реального времени. Активация фаз, их режимы, вход/выход,
  переходы между экземплярами и задержки должны подтверждаться отдельно.
- Ключ существующего geometry cache сохраняет точные float-входы hatch,
  толщины, угла выборки и datum Z в round-trip представлении, SHA,
  порядок/тип тел и включение контуров.
  Округление компактного снимка не разрешает округлять входы ключа.
  Контракт ключа v5 не использует старые ключи как fallback;
  прежние записи/прогнозы сохраняются, новая геометрия вычисляется при miss.
- `metadata_json.scan_strategy` задаёт поддержанные параметры конкретной
  карточки поверх настроек машины/пресета; источник фиксируется отдельно.
  `contours_enabled` — настоящий boolean, `hatch_angle_deg` — угол выборки,
  не доказанная последовательность послойного поворота. Оба поля входят в
  geometry cache и configured-scan-v2 scope. Выключенные контуры не требуют
  неиспользуемой скорости. Не принимайте один снимок выбранной детали за
  подтверждение режимов всех экземпляров на платформе.
- Калибровка привязана минимум к материалу и толщине слоя; не переносите модель
  между несовместимыми режимами.
- Автокалибровка времени выполняется owner-local заданием `time_calibration`:
  `calibration_inputs.py` копирует общие карточки/слои, затем после закрытия БД
  `calibration.py` считает, а `worker/calibration_tasks.py` публикует. Финальная
  запись сверяет fingerprint входов и всех настроек, затем lease/generation
  (после ожидания блокировок). Поправки, статус и результат задания атомарны.
  Изменившиеся входы требуют нового расчёта, не перезаписи старым результатом.
- `analytics/prediction/scan_fitting.py` — единая локальная численная реализация
  NNLS, geometry-held-out проверки, robust cycle fit и их порогов. Она не
  читает SQL/MinIO/raw и не пишет настройки. `scan_calibration.py` собирает
  допустимые входы/отчёт и сохраняет совместимые экспорты, затем publisher
  атомарно применяет результат. Разделение файлов не меняет смысл модели или
  доказывает held-out точность цикла; её проверка по-прежнему отдельный долг.
- HTTP и завершение импорта только ставят калибровку в очередь. Pending-запросы
  объединяются на одном ПК; событие во время running создаёт следующий запрос.
  `POST /prints/recalibrate` — контракт v2, HTTP 202 + job_id, не «уже применено».
  `GET /prints/prediction-accuracy` не обучает NNLS и показывает статус последнего
  фонового расчёта. Устаревшие входы/версия аналитики скрывают прежние кандидаты.
- Фоновая калибровка и страница точности используют только общие LayerSnapshot;
  отсутствие строк явно неизвестно, не повод читать локальную копию логов.
  Legacy sync-функции оставлены для совместимости тестов/исследований; не
  вызывайте `recalibrate_*_and_apply(db)` из production HTTP/импорта.
- Общий допуск геометрических прогнозов к калибровке находится в
  `analytics/prediction/input_quality.py`: неполная геометрия/поддержки,
  неподтверждённый datum Z, неподтверждённая связь с логом и устаревший снимок
  исключаются из scan/time. Измеренный прожиг/нанесение остаются в истории;
  независимая калибровка нанесения и цикла только по логам не зависит от STL.
- `print_hours` в сохранённых снимках и историческом отчёте точности — старый
  подытог «прожиг + нанесение». `machine_cycle_hours` — полный нормальный цикл.
  Не смешивайте их в процентах ошибки или доверительном интервале. `null` факта
  не преобразуется в нулевое время или нулевую ошибку.
- Сравнение в каталоге/карточке — `print_cards/comparison.py`, summary v2.
  Обе страницы используют один `comparison_scope/status/coverage`; frontend не
  восстанавливает факт из machine_min или wall-clock. Карточка и старый контур
  accuracy/ratio используют `timing_validation.has_complete_layer_coverage`:
  нужны ровно все ожидаемые слои 1..N из проверенного общего снимка. Без N или
  при пропуске одного слоя полной суммы нет. Частичные слои могут обучать
  послойный scan, но не метрику времени всей печати. Для полного normal cycle
  нужен независимо опубликованный accounting
  того же поколения; нельзя строить «факт» из параметров текущего прогноза.
  Частичные суммы и wall-clock остаются диагностикой без процента ошибки.
- `calculation_inputs.parameter_sources` сообщает источник настроенного числа,
  а не подтверждение реального режима. Нельзя считать значение проверенным
  только потому, что оно давно сохранено в карточке или пресете.
- Одинаковая геометрия, напечатанная повторно, является полезным повторным
  измерением, но все её повторы должны попадать в один holdout-блок при
  cross-validation. Ошибка внутри блока считается отдельно для каждой печати,
  чтобы противоположные ошибки повторов не погашались до принятия модели.
- Применимость калибровки и свежесть входов публикации — разные проверки:
  новый hash карточки не делает старые абсолютные beta пригодными к новой
  скорости/стратегии. `scan_scope.py` сохраняет версионированный состав
  настроенных scan-входов в снимке и NNLS-артефакте: физическую машину, материал,
  толщину, скорости/переходы, hatch, лазеры и доступные ID пресета/стратегии.
  Только полное совпадение допускает применение; короткий legacy-ключ не
  является fallback. Не достраивайте старый scope из текущих настроек.
  Совпадение настроек не подтверждает as-run рецепт: read-only экспорт задания,
  phase-recipe для цикла/нанесения и сужение старой ratio-калибровки ещё нужны.
  Противоречие printer_id снимка и связанной сессии запрещает scan/cycle fit;
  физическая машина не выводится из имени операторского ПК.
- У `max(burn + pour + base, floor)` base и floor имеют раздельную
  идентифицируемость. `max_base_floor_v2` не допускает null base к применению;
  только floor-слои не определяют base. Аддитивная ветка без известного floor
  требует меняющихся данных свободной ветки и не применяется к слоям с суммой
  burn+pour ниже её сохранённой области. V1/legacy additive не повышаются до
  v2 сменой строки версии: нужна новая калибровка. Это не заменяет held-out
  проверку cycle, которая ещё не реализована. Не заменяйте
  неизвестный normal target результатом проверяемой модели и не выдавайте
  post-hoc реконструкцию за сохранённый до печати прогноз. Следующий план и
  воспроизводимые ограничения: `docs/reviews/2026-09-23_time_prediction_strategy.md`,
  реализованные защиты — `docs/reviews/2026-09-26_time_prediction_guards.md`.
- Аномалию слоя связывайте с высотой Z и реально активной геометрией/деталями;
  если размещение/ориентация неизвестны, явно помечайте вывод как приближённый.
- `analytics/geometry_context.py` один раз на вызов готовит равномерную
  геометрическую reference-сетку для относительной длины траекторий и список
  измеренных слоёв для progress-привязки. Не заменяйте reference медианой
  неравномерных boundary samples; число перескоков не является длиной.
  Порядок Python-сложения, datum, интервалы присутствия и пометки точности
  привязки сохраняются; это отображение снимков, не новая оценка времени.
- Не угадывайте начало координат построения. Если нативные поддержки Magics не
  декодированы, `Z=0` и `min Z` являются разными гипотезами. Используйте явно
  сохранённый `build_origin_z_mm`; без него показывайте диапазон/предупреждение,
  а не молча добавляйте или отбрасывайте пустые слои.
- Фото MasterSLM 2.0.6.033 и STL рукоятки с 160 282 гранями независимо
  подтвердили для одной сохранённой компоновки: `min Z=3`, `max Z=193`, слой
  0,060 мм и показанные слайсером 3 217 слоёв соответствуют
  `ceil((max Z - build_origin_z)/thickness)` при `build_origin_z=0`, а не высоте
  самого тела. Не переносите это начало координат на другой проект без его
  экспорта или операторского подтверждения.

## Импорт слайсера M350

- `PrepareModel` / `MasterSLM` сохраняют параметры в SQL-структурах
  `Projects`, `Models`, `Presets`, `HatchsStructure`, `EquidistantsStructure`,
  `SupportsStructure` и `ConesStructure`. Наличие имени поля в EXE не
  доказывает его единицу, шкалу, бинарный offset или порядок применения.
- Правила восстановленного EXE привязываются к SHA и версии, а не ко всему
  семейству MasterSLM. Исследовательский replay LaserStudio отделён от
  production-оценщика: переключатель `titan` в функции выбора угла не доказывает
  материал. Сохраняйте signed integer division к нулю и порядок tabu-поправок;
  индекс сечения нельзя молча считать номером физического слоя time.log.
- Одинаковое имя `isBurnThroughOne` в `SupportsStructure` и `ConesStructure`
  не доказывает одинаковый алгоритм. Периодичность cone-векторов не является
  доказательством периодичности обычных поддержек или активного thermal-bridge
  режима другой версии. Назначения моделей лазерам на скриншоте подтверждают
  распределение, но не одновременное исполнение каналов.
- Не принимайте неизвестный экспорт PrepareModel по расширению: пока не
  подтверждены сигнатура и сериализация, неизвестный `.data` / `.3data` /
  `.contours` / `.3dvector` / `.vi` / `.paths` должен быть сохранён как
  непрочитанный источник с SHA-256, а не интерпретирован как набор float.
- `.magics` — брендированный ZIP (`MT` вместо `PK`); перед извлечением
  проверяйте сигнатуру и CRC. Вершины печатных тел — int32 LE в 0.0001 mm.
  Текущий `magics_reader` извлекает mesh blocks, но не размещение/экземпляры
  из `header.xml`. Количество прочитанных тел не является количеством деталей
  платформы. `geometry_quality.missing` сохраняет это ограничение даже при
  наличии Support-STL. Успешная каталогизация (`desktop_catalog_complete`)
  не подтверждает полную геометрию (`desktop_geometry_complete`).
  Нативные `SupportSurfaces_*` не являются обычным мешем: без экспортированных
  `s_*.stl` оценка времени — нижняя граница.
- `*_time.log` — подтверждённый источник реальных `pour_ms`, `burn_ms` и
  `make_layer_ms` на слой. Проверяйте `OLD_STATS` по абсолютным `NEW_STATS`.
  Полный цикл может включать pause-like выбросы: для нормального прогноза
  выделяйте штатный overhead и minimum-layer-cycle, не усредняйте wall-clock.
- Дату Magics/проекта и дату лога нельзя использовать как доказательство пары.
  Нужен сильный независимый признак (подтверждённый fingerprint, число слоёв
  или явная загрузка из карточки).

## Сопоставление карточки и логов

- `print_linking` выбирает незанятые сессии общим SQL `NOT EXISTS` по всем
  карточкам, включая другие ПК. Auto-link/candidates дополнительно ограничены
  владельцем; список unlinked остаётся общим чтением. Занятые context не
  загружаются для последующего Python-фильтра. Это только отбор кандидатов:
  финальные row locks и уникальное ограничение связи остаются обязательными.
- Совпадение даты только создаёт список кандидатов и не доказывает пару.
- Для автоматической связи требуется независимый сильный признак: явная
  загрузка логов из карточки, согласованное число слоёв либо подтверждённый
  fingerprint компоновки; неоднозначность оставляется оператору.
- `log_import_hint.date` не доказывает загрузку конкретной сессии в карточку.
  Подтверждение явного импорта опирается на цепочку карточка → завершённое
  `ImportJob` → единственная сессия и сохраняет ID задания. Старое доказательство
  метода `operator_import_hint` без ID задания не допускает геометрическую
  калибровку. Доказательство другой `session_id` также не подтверждает текущую
  связь, даже если старый флаг `session_link_confirmed=true` сохранился.
- Подтверждение связи сохраняется вместе с `session_id` и способом в
  `session_link_evidence`. Явная загрузка из карточки/ручной выбор и новая сильная
  связь заменяют неподтверждённый статус черновика. Отвязка удаляет старое
  доказательство; перенос связи без доказательства не переносит подтверждение.
- Нельзя выбирать пару по совпадению фактического времени с текущим прогнозом:
  это круговая утечка, которая затем ложно улучшит метрику этой же модели.
- Границы ежедневных/возобновлённых логов с одинаковой записью слоя считаются
  один раз. Материально отличающийся повтор того же номера — отдельная попытка,
  но этот слой исключается из калибровки нормального прожига.
- Сверка `OLD_STATS`/`NEW_STATS` привязана к соседним записям одной попытки,
  а не к порядковому номеру записи внутри слоя. `timing_valid=false` запрещает
  использовать summary в калибровке. Единый отбор находится в
  `analytics/prediction/timing_validation.py`; применяйте его сразу ко всем
  суточным файлам сессии, до фильтрации отдельных значений по диапазону.
- Сохранённые `LayerSnapshot` проходят тот же допуск, что события парсера:
  известная ошибка, неконечное число и конфликтующие повторы не обходят фильтр
  через БД. Если строки есть, но отклонены, нельзя молча подменить их локальным
  файлом. Остаток цикла рассчитывается из согласованных burn/pour/make, а не
  из потенциально устаревшего кэшированного `normal_overhead_ms`.
- Дата имени сенсорного файла — дата открытия записи. Один файл может
  продолжаться несколько суток (`18.07.2026_sensors.log` до 21 июля).
  Сначала восстанавливайте все переходы через полночь, затем ограничивайте
  интервал и прореживайте график. Не приклеивайте дату имени ко всем строкам.
- При дыре ровно в один граничный слой продолжение можно склеить только по
  независимой физической непрерывности позиции стола и шага слоя. Реальный
  пример 17→18.07: основной лог содержит слой 299 в `-62690`, следующий начинает
  слой 301 в `-62810` при шаге 60; строки времени 299/300 отсутствуют и не
  считаются измеренными.

## Слайсер M350

- На исследованной поставке MasterSLM/PrepareModel параметры проекта и стратегий
  читаются из Microsoft SQL Server. Локальный `policy.db` содержит только
  настройки видимости интерфейса; не принимайте его за базу режимов.
- Подтверждённые статическим анализом сущности: `Projects`, `Models`,
  `EquidistantsStructure`, `HatchsStructure`, `SupportsStructure`. Для расчёта
  нужен их версионированный read-only экспорт без секретов.
- `settings.db` поставки может содержать привилегированные реквизиты SQL Server
  открытым текстом. Никогда не переносите их в код, отчёты или логи; используйте
  отдельную учётную запись только на чтение и ротацию обнаруженного секрета.

## Миграции и схема

- Alembic — единственный источник истины production-схемы. `create_all()` только
  для тестового harness.
- Новая миграция продолжает единственную цепочку из текущего head. Не создавайте
  параллельные heads.
- В NAS-режиме миграция запускается один раз отдельным сервисом `migrate`; API и
  worker выполняют только `assert_schema_at_head()`.
- Миграции должны работать и на PostgreSQL, и на SQLite, если нет явно
  задокументированного исключения.

## Основные точки входа

- API: `api/main.py`, маршруты в `api/routes/`.
- Чтение сессий: `storage/repositories/session_reads.py` (SQL-only),
  отчёты: `storage/repositories/reports.py` (SQL-only),
  `domain/services/session_reports.py` (MinIO после закрытия SQL).
  GET сессии/отчёта не разбирает raw, не пишет результаты и не держит
  process-local кэш аналитики. Legacy RuntimeRepository сохраняет SQL-write
  обязанности, но больше не открывает исходники и объекты MinIO.
- `domain/services/session_sources.py` владеет raw mirror/rehydration.
  `SessionReadsRepository.sources_snapshot` копирует только metadata источников
  и владельца; standalone use-case освобождает SQL до проверки/разбора файлов.
  Owner проверяется до raw IO. Старые синхронные исследовательские адаптеры
  калибровки сохраняют caller UoW; production использует detached CalibrationInputs.
  Любое сохранённое timing evidence, включая пустое/отклонённое, запрещает fallback.
  Доступный unparsed источник сверяется с записанными SHA-256/размером и
  проверяется на изменение при хешировании/парсинге. Несовпадение и известная
  порча immutable mirror требуют повторного импорта, не выдаются за отсутствие
  файла и не разрешают maintenance публиковать частичный результат.
- Maintenance overview/time/timing читает detached сессию, считает вне SQL и
  перед записью блокирует и сверяет владельца/весь входной снимок. Современный
  анализ или отчёт ремонтируется исходным ImportJob, не частичной заменой JSON.
  Timing-only legacy manifest без source не является полной публикацией анализа:
  legacy overview/time repair оставляет его и LayerSnapshots неизменными и не
  добавляет analysis_snapshot без согласованных артефактов.
- `replace_layer_timings` получает уже заблокированную BuildSession той же
  SQLAlchemy Session. Publisher держит все parent rows до завершения и не
  загружает большие context повторно; standalone legacy adapter сам блокирует
  parent. Проверки owner/token/lease остаются у соответствующего use-case.
- Обычные события пишутся идемпотентными parameter batches до 500 строк через
  Core table INSERT/ON CONFLICT + executemany, без ORM-пропуска явных NULL.
  Шаблон имеет bind-параметры одной строки, а не 500 копий; старый предел SQLite
  не требует отдельного размера пакета. PostgreSQL с psycopg 3 и libpq 14+
  использует встроенный pipeline: это пакет операций драйвера, не один SQL-
  statement на все строки. Last-duplicate-wins, первоначальный created_at,
  caller commit/rollback и authoritative import fence сохраняются. Нельзя
  укрупнять транзакции или заменять событие неподтверждённой агрегатной строкой.
- ZIP и папка с ZIP имеют один parse-tree expansion после архивирования raw.
  `expand_log_inputs` возвращает object refs, member paths и SHA-манифест,
  рассчитанный во время копирования. Ingestion независимо хеширует развернутые
  файлы для проверки изменения после подготовки; CRC/lease/лимиты обязательны.
  `_prepared_import_sources` в том же import_jobs.py владеет подготовкой и
  временем жизни своей TemporaryDirectory: файлы доступны всему анализу,
  выход/ошибка удаляет только временное дерево, не исходную папку/архив.
  `_prepare_group_artifacts` в том же файле собирает сводку и отчёт одной группы
  из одного PreparedSessionAnalysis, без SQL и NAS-записи. Staging событий,
  mirror и authoritative fencing остаются вне этого вычислительного шага;
  отчёт сохраняет собственное mutable-дерево log_insights, не alias сводки.
- Экспериментальный `/test-metrics/latest` выбирает только собственную сессию
  ПК; явный чужой session_id отклоняется до открытия файлов. SQL освобождается
  до локального ML. Ограниченный cache привязан к metadata и размеру/mtime файла,
  обновление принудительно доступно через refresh; cache lock не охватывает ML.
- Чтение отчёта по историческому ID возвращает его собственную публикацию,
  не последний отчёт сессии. Идентификаторы SQL-сводки/полного объекта и их
  analysis_snapshot/timing_publication должны совпадать. Недоступный MinIO
  допускает bounded SQL-копию при чтении, но не замену известного полного
  отчёта этой копией при LLM-дополнении. Legacy без URI уже может быть неполным.
  Полный скачанный JSON уже detached; SQL-копия дополнительно копируется только
  при реальном fallback, чтобы не менять исходный fingerprint LLM-публикации.
  Список сессий выбирает только runtime_payload.group, не исходные files;
  filtering/count/order/pagination остаются SQL-only.
- Предпросмотр timeline отбирает head/priority/sample одним разделением потока;
  порядок и все priority events сохраняются даже при превышении sample cap.
  Число показанных фактов не включает служебный `_truncated` sentinel.
  Оригинальный полный timeline не изменяется и остаётся в объекте отчёта.
- LLM-дополнение: detached отчёт/контекст и проверка владельца → закрыть SQL →
  ожидать модель и загрузить immutable объект → коротко заблокировать сессию,
  затем отчёт → заново проверить владельца, поколение и fingerprint обоих
  входов → commit. Параллельное дополнение/пересчёт возвращает конфликт;
  устаревший результат не перезаписывает отчёт. ReportsRepository только
  читает/публикует подготовленные артефакты; не делает IO, commit или close.
- `domain/services/session_requests.py`: ingest/analyze/reanalyze — контракт v2,
  HTTP 202 и ID задания, а не синхронно готовый отчёт. Повторный анализ использует
  исходный ImportJob и штатную публикацию. Если у legacy-сессии нет доказанной
  связи с заданием, требуется загрузить исходники заново; путь не угадывается.
  `/reports/generate` только форматирует опубликованный результат.
- Browser upload: `importing/uploads.py` сохраняет квитанцию schema v2 с
  исходной политикой подтверждения. `importing/recovery.py` в import worker
  примерно раз в 30 секунд восстанавливает только собственные прямые receipts
  из incoming: сначала immutable job ID, затем SHA/размер/состав файлов без SQL,
  затем общий с HTTP `publish_prepared_browser_upload` под блокировкой.
  Существующий job/lease/generation не перезаписываются. V1 без задания требует
  подтверждения оператора. Ошибка NAS получает backoff; recovery не удаляет
  исходники. `needs_attention` нельзя молча превращать в успешный импорт.
- Карточки и вложения: `domain/services/print_cards/`. `cards.py` — создание,
  правка с expected_revision, чтение и удаление; `validation.py` — правила
  полей; `attachments.py` — staging/SHA, NAS-outbox, публикация и скачивание.
  HTTP переводит `CardError` в ответ, не содержит файловую/каталожную транзакцию.
- HTTP-загрузка и NAS-sync используют один `publish_attachment`: после передачи
  заново читается и блокируется карточка, проверяется владелец геометрии; файл,
  подсказка даты (только если дата всё ещё пуста) и задание прогноза атомарны.
  Владелец задания берётся из операции, не из неявных настроек другого процесса.
- Удаление карточки/вложения фиксируется сервисом до выдачи работы на очистку.
  Нельзя полагаться на порядок `BackgroundTasks` и завершения request dependency:
  фоновая задача может начаться раньше commit. При ошибке commit объект сохраняется.
  Очистка проверяет ссылки других карточек; при недоступной БД/MinIO оставляет
  объект и пишет ошибку. Это best-effort очистка, не долговечный сборщик мусора.
  `files_removed` считает снятые связи карточки, не обязательно удалённые объекты.
- Чтение карточки/скачивание и HTTP upload/delete являются самостоятельными
  use-case границами: передавайте чистую сессию, не чужую транзакцию с правками.
  Чтения освобождают SQL до отображения геометрии/передачи файла; upload/delete
  владеют финальным commit. Общий `publish_attachment`, напротив, не коммитит:
  NAS-worker включает его в свою короткую транзакцию.
- Контроль качества карточки и чтение операторского отчёта —
  `domain/services/print_cards/quality.py`. Итог контроля, owner-local задание
  переобучения и revision карточки коммитятся атомарно; HTTP инвалидирует кэш
  отчёта только после успешного commit. Связь с сессией читается из заново
  загруженной и заблокированной карточки, не из устаревшего ORM-объекта.
  История и входы отчёта копируются; SQL освобождается до построения отчёта.
  Эти use-case также требуют чистую сессию, без чужих несохранённых правок.
- Импорт логов: `worker/tasks.py`, `domain/services/ingestion.py`, `parsers/`.
- Приём браузерных логов из карточки и общей формы — один use-case
  `domain/services/importing/uploads.py`, без зависимости от HTTP-маршрутов.
  Потоки файлов обрабатываются вне SQL; перед публикацией карточка заново
  читается под блокировкой и проверяется владелец. Задание, уведомления и
  подсказка даты/метаданные коммитятся вместе до успешного HTTP-ответа.
- Браузерные пакеты лежат в `raw_logs/incoming/.browser-upload-*` на общем
  локальном mount API/worker. Их читает только явно поставленное задание;
  обход предка через `core/utils/files.py:iter_source_files` исключает такие
  каталоги и служебные файлы. Не заменяйте его безусловным `rglob`: watcher и
  ручной rescan не должны смешивать пакеты разных карточек или видеть недогрузку.
  Имена нормализуются для macOS/Windows без потери даты и суффикса типа лога;
  разные байты не перезаписываются, даже если запасное имя уже занято.
- При неопределённом commit приёма логов сохраняются пакет и соседняя JSON-
  квитанция с owner/card/job ID и SHA-256. Нельзя удалять/перемещать исходники:
  сервер мог принять commit без ответа. Сначала сверяйте задание по ID из
  квитанции. Автоматическое восстановление регистрации выполняет recovery;
  зарегистрированные задания повторяет штатный owner-local worker.
- Контракты, staging и публикация импорта — `domain/services/importing/`;
  совместимые точки входа и подготовка остаются в `domain/services/import_jobs.py`.
  `persistence.py` записывает исходные события короткими fenced-пакетами,
  `publication.py` атомарно сохраняет готовые слои, сводку, отчёты и завершение.
  Отчёты загружаются и проверяются до открытия финальной SQL-транзакции.
- `importing/requests.py` — единственная регистрация найденного пакета и
  переходов confirm/ignore/postpone/retry. Startup, rescan и agent detection
  вызывают `register_import_candidates`: все папки подготовлены до открытия
  общей короткой SQL-транзакции. Нет optional чужой транзакции, route-to-route
  регистрации или записи sessions/reports при подтверждении; расчёт и fenced
  публикация остаются у worker. Browser receipts имеют отдельный контракт
  восстановления и используют свой общий publisher, не обходят эти защиты.
- Компактные измерения версионируются манифестом `timing_publication` в context
  сессии и `publication_id` в строках слоёв. Проверяются generation, число строк
  и fingerprint. Завершённые `empty` / `no_time_log` не разрешают сырой fallback;
  несовпадение манифеста/строк также не означает «ещё не разбирали».
  Общий допуск — `analytics/prediction/timing_snapshot.py`: чистая
  `read_timing_publication` одной обязательной проверкой возвращает статус и
  события. Нет отдельного unchecked/trusted пути; разные потребители не должны
  повторно считать fingerprint ради получения того же статуса.
  Отсутствие legacy-снимка возвращает `absent/None`, известное пустое/невалидное
  evidence — статус с пустыми событиями, не разрешение raw fallback.
  Физический допуск фаз остаётся отдельным: `calibration_timing_payloads`
  вызывается один раз на все события сессии перед численными проекциями.
  `timing_components_ms`, `calibration_burn_ms` и `calibration_cycles_ms`
  принимают этот набор payloads и сохраняют свои разные границы допуска.
  Нет optional/trusted обхода или автоматического смешения events/payloads.
  `CalibrationInputs.timings` заменяет промежуточные events, сохраняя ключи
  известных пустых/невалидных сессий; fingerprint строится из исходных строк
  и манифестов, не из отфильтрованных проекций.
  Старые строки без манифеста и тега читаются совместимо, но не объявляются
  новым проверенным снимком.
  Перед заменой также сверяется исходная версия сессии: другое задание того же
  ПК не должно молча перезаписать результат, изменившийся за время расчёта.
- Тяжёлый расчёт времени: `worker/estimate_tasks.py`, сценарии в
  `domain/services/estimation/`, геометрия — `analytics/prediction/plate_estimator.py`.
  `inputs.py` читает отдельную копию входов; `requests.py` проверяет допуск и
  ставит задание; `calculation.py` выполняет локальный расчёт; `publication.py`
  атомарно сохраняет прогноз и завершение задания. Worker и синхронизация NAS
  не импортируют HTTP-маршруты; `EstimateError` переводится в HTTP только в API.
- HTTP-прогноз и загрузка геометрии только создают долговечное owner-local
  задание во всех окружениях, включая `APP_ENV=test`. Нет второго API-пула,
  синхронной тестовой публикации или implicit background calculation. Тест
  сначала проверяет постановку задания, затем запускает штатный consumer.
- Повторный запрос расчёта присоединяется к pending/running заданию с тем же
  владельцем, revision/геометрией и снимком настроек/пресета. Создание запросов
  сериализуется свежим parent row lock карточки; lease/generation не меняются.
  После завершения ручной пересчёт создаёт новый запрос. Изменение параметров
  не разрешает присоединение к прежнему расчёту и не отменяет финальный fencing.
  `calculation.py` не принимает SQL-сессию; исторический интервал вычисляет
  только `enrich_prediction_interval(..., inputs=CalibrationInputs)` после
  освобождения БД. Внутренние тесты импортируют сервис, не private API-адаптер.
- Перед публикацией прогноза повторно сверяются revision и hash входов:
  карточка, ссылки/SHA геометрии, эффективные настройки и пресет. Изменения
  параметров/пресетов, калибровка и публикация используют общий короткий
  `lock_estimation_configuration`; создание/удаление default-пресета также
  защищено. Порядок зависимых блокировок: конфигурация → сессия → карточка.
  Проверка lease повторяется после ожидания блокировок и после записи карточки;
  late expiry вызывает исключение и откат, а не выход с частичным commit.
- История для интервала прогноза читается коротко через `CalibrationInputs`;
  статистика считается после закрытия SQL-соединения. Её fingerprint хранится
  в `interval_reference`. Интервал scan+recoat нельзя выдавать за интервал
  полного цикла с overhead/minimum-layer-cycle.
- Безопасное переобучение: `worker/model_tasks.py`,
  `analytics/prediction/retraining.py`, реестр в
  `storage/repositories/model_registry.py`.
- Отчёт: `reporting/json_report/generator.py`.
- Общая БД: `domain/models/`, `storage/repositories/`, `migrations/versions/`.
- NAS deployment: `deploy/nas/`.
- Первоначальный комплект NAS для Mac готовит `deploy/nas/prepare-mac.command`:
  фиксированные revision/SHA-256 compose, секреты создаются один раз, повторный
  запуск проверяет прежний архив. Это не обновление работающей БД: существующие
  пароли и пути данных сохраняются. При смене закреплённого compose обновлять
  revision и SHA вместе и проверять `tests/test_nas_install_bundle.py`.
- Диагностика NAS без SSH: `deploy/nas/diagnose-no-ssh.sh` запускается вручную
  через DSM Task Scheduler и создаёт только новый отчёт, без значений `.env`.
  Не трактуйте HTTP реестра, наличие env-поля или статус контейнера как проверку
  скачивания образа, пароля или записи данных. Тесты: `tests/test_nas_diagnostics.py`.
- Послойная диагностика: `analytics/log_insights/`; поток исходных сенсоров,
  воздействие среды, восстановление, баланс времени, сравнение повторов и карта
  контроля. Порог профиля предварительный, пока явно не подтверждён оператором.
  Не интерполируйте длинные пропуски и не превращайте неизвестный остаток в паузу.
- Карточка диагностики: `domain/services/log_insights.py`,
  `GET /analysis/prints/{record_id}/log-insights`, `web_assets/log-insights.js`.
  NAS читается коротко; сравнение выполняется после закрытия транзакции.
  Допустимые времена подготавливаются один раз для каждой выбранной сессии
  внутри запроса и используются остатком, сравнением и provenance. Это не
  межзапросный кеш; целостность опубликованных слоёв проверяется прежде.
  Без достоверного ключа компоновки/режима кандидаты повторов не читаются,
  но измерения и диагностика самой карточки остаются доступны. Баланс времени
  использует исходное evidence попыток, не заменяется отфильтрованным словарём.

## Работа с репозиторием

- `pyproject.toml` — источник деклараций зависимостей и Docker tiers/pins.
  `requirements.*.txt` генерируются `python scripts/export_requirements.py`;
  перед сборкой/CI проверяются `--check`. Это не полный transitive lock.
  Контейнерные pins Python 3.11 не подменяют native-диапазоны macOS/Windows.
- Build manifest включает версию, SHA, source_state, build date и build ID.
  Release SHA вычисляется после version commit. Launcher проверяет identity
  запущенного API и `/health/ready`, не только успешную команду Docker.
- Публикация контейнеров — `.github/workflows/release.yml` по тегу `vX.Y.Z`:
  VERSION должен совпасть с тегом, а CI именно этого SHA завершиться успешно.
  Сначала собираются все сервисы, затем публикуются versioned-теги и только
  после них compatibility aliases. Текущие готовые образы — linux/amd64;
  нативный ARM-запуск собирается отдельно из исходников. GitHub Release
  публикуется после успешной сборки/выгрузки, не только после git push.
  Информация о релизе хранится в `docs/releases/`; ограничения точности времени
  нельзя закрывать формулировкой «тесты прошли».
- Release workflow передаёт verified `operator-images.json` в reusable desktop
  workflow; Mac ARM/Intel и Windows installers связаны с тем же full SHA и
  immutable digests. Release/установщики публикуются только после native smoke
  и Docker lifecycle. Unsigned test-пакеты не публикуют public update feed.
  Инструкция оператору и порядок выпуска — `docs/OPERATOR_GUIDE.md`.
- Linux не является отдельной целевой операторской системой. Проверки внутри
  Linux-контейнера относятся к внутренней среде Docker, используемой запуском
  на ПК оператора, а не к развитию отдельной Linux-версии продукта.
- Сохраняйте чужие незакоммиченные изменения; не используйте destructive git
  commands без явного запроса.
- Для поиска используйте `rg` / `rg --files`, для точечных правок — `apply_patch`.
- Поддерживайте обратную совместимость API и сохранённых JSON, если изменение не
  сопровождается миграцией/явной версией контракта.
- Публичные операторские названия и выводы — на понятном русском; внутренние
  идентификаторы могут оставаться английскими.

## Операторский интерфейс

- Настольная оболочка macOS/Windows находится в `desktop/`. Это одно окно
  Electron и короткоживущий встроенный host CLI (`core/updating/`), не отдельная
  служба. Dashboard iframe не получает privileged IPC, Node или Docker socket;
  команды принимает только точный доверенный main frame с packaged file URL.
- Пакет приложения и данные разделены: `.app`/Program Files можно заменить,
  `.env`, compute-node ID, operator state/outbox и storage mounts нельзя.
  Импорт старой установки сохраняет её корень. Тестовое приложение имеет
  отдельные appId/userData, без подписанного публичного канала обновлений.
- Native update сначала проверяет/скачивает пакет, затем `prepare-restart`
  завершает уже принятые HTTP/outbox записи и проверяет owner-local jobs до
  закрытия renderer. `restart_ready` — восстанавливаемое состояние, не успешное
  переключение. Новый пакет приводит backend к full SHA и immutable digests
  собственного манифеста; прежняя версия доступна при отложенном обновлении.
- Обычный запуск стартует точные остановленные контейнеры, но не делает
  Compose up на работающем расчёте. Storage-only NAS, чужой/удалённый Docker,
  изменившиеся mounts/секреты и неизвестный drain-протокол блокируют переключение.
  Никаких автоматических NAS migration, `down -v` или пересоздания БД.
- Все сценарии quiesce, включая native stop/restart, проверяют прежний Docker
  context/daemon до изменений. Отказ до переключения проходит один общий
  abort: возобновить consumers → снять только собственный maintenance gate.
  Если cleanup не подтверждён, сохраняются журнал и fencing token; нельзя
  объявлять восстановление успешным или освобождать чужой gate.
- Принятые mutating HTTP-запросы и локальная публикация outbox удерживают общую
  OS write-admission блокировку до завершения, включая ASGI background work.
  Maintenance gate закрывает новые записи; shared/exclusive locks обеспечивают
  drain старых. Это протокол Linux-контейнера, не native Windows flock.
- PyInstaller host собирается отдельно на каждой целевой ОС/архитектуре.
  Подписанный public build требует сертификата/нотаризации и проверенных
  container digests; unsigned test не считается доказательством автообновления.
  Приёмка и переход с pre-protocol установки — `docs/DESKTOP_APP.md`.

- Основной визуальный язык — тёплая тёмная производственная панель без теней:
  фиксированная боковая навигация, терракотовый акцент, моноширинные подписи к
  данным и русские названия действий/показателей.
- Домашняя страница строится вокруг карточек печатей и настоящего STL-превью;
  агрегированные графики не должны вытеснять текущую работу оператора.
- Каждый рабочий экран обязан иметь состояния загрузки, отсутствия данных и
  ошибки. Данные берутся из API; демонстрационные числа нельзя выдавать за факт.
- На экране аномалий отделяйте наблюдение от причины. Частота совпадений в
  похожих печатях — контекст, а не доказательство причинности.
- Кнопки загрузки из карточки всегда прикрепляют файлы к открытой карточке, а
  не создают новую. Переключатели ракурса STL должны реально менять камеру.
- Целевая структура интерфейса и порядок выноса монолитного JavaScript описаны
  в `docs/DASHBOARD_ARCHITECTURE.md` и `docs/IMPLEMENTATION_PLAN.md`.
- GET `/` — SQL-free HTML-оболочка, не предварительная загрузка всей истории.
  Исторические панели загружают bounded read models при открытии, страницы
  максимум по 100 строк; каталог сохраняет 10 карточек + «Ещё».
  CSS/JS — `web_assets/dashboard/`, библиотеки/шрифты с manifest SHA и лицензиями
  — `web_assets/vendor/`. Недоступность Chart/Three не ломает базовые действия.
  Сценарии пока classic scripts с общими globals; это не полная компонентная
  изоляция и не повод подключать второй независимый frontend stack.
- Имена файлов/карточек, заметки и материалы — данные, не HTML или исходный JS.
  Экранируйте текст/атрибуты один раз; идентификаторы в URL кодируйте отдельно.
  Не передавайте пользовательское имя в строке inline onclick: HTML-декодирование
  `&#39;` возвращает кавычку до исполнения JS. Используйте listeners/замыкания,
  как в `card-files.js`; регрессии — `tests/web/card-time.test.cjs`.

## Приоритетный технический долг

Карта переходов доверия и очередность исправления решений находятся в
`docs/DECISION_ARCHITECTURE.md`. Owner-local калибровка вынесена из транзакций
импорта и HTTP-запросов. Компактные слои и сводка публикуются атомарно с fencing;
исходные события пока записываются отдельными идемпотентными пакетами, не единым
поколением всей истории. Canonical events читаются также raw SQL в MCP и export;
отсутствие ORM-import не доказывает отсутствие потребителя. Миграция поколений
событий требует согласованного изменения этих читателей, не удаления истории.
Единая измеренная сводка для отчёта, риска и карточки введена как analysis_snapshot.
Основной worker расчёта уже использует узкие сервисы,
не HTTP-маршруты. Не считать финальный fencing защитой любых более ранних записей.

Дальше разделять `api/routes/prints.py`: прогноз вынесен в `estimation/`,
основные сценарии карточек/вложений и качество/отчёт — в `print_cards/`.
Приём логов обеих форм — в `importing/uploads.py`.
Каталог подготавливается в `print_cards/cards.py`: страница, вложения и count
читаются до освобождения SQL и формирования сравнения; локальная математика
не открывает транзакцию снова. SSE остаётся HTTP-транспортом; один poller на
процесс и baseline для каждого нового подписчика, затем изменения.
Карточка читает только ID/статус фонового задания, не его input/result JSON.
`print_cards/comparison.py` использует свежие SQL-column проекции без второй
глубокой копии каждого слоя. Это не разрешение возвращать caller/ORM mutable
деревья без отделения; generation/digest проверки и закрытие SQL обязательны.
Старый API sync-путь расчёта
удалён после переноса его тестов к сервисам и штатному worker. Переносить
оставшиеся сценарии по одному; не сохранять второй путь лишь ради monkeypatch
старого теста. Долговечную очередь
очистки невостребованных объектов добавлять отдельно, с учётом всех ссылок.
Дальше разделить оставшиеся SQL-write обязанности широкого
`storage/repositories/runtime.py`; SQL-read сессий уже выделен. JavaScript вынесен
из HTML по сценариям, но общие globals и inline handlers ещё требуют изоляции.
Подробный порядок и критерии находятся в `docs/IMPLEMENTATION_PLAN.md`, этап 9.

SQL-only обнаружение/чтение/lease заданий импорта находятся в
`storage/repositories/import_jobs.py`. Все потребители вызывают его напрямую;
import delegates и private aliases в RuntimeRepository удалены. Репозиторий
не зависит от FastAPI, не делает commit/close и не запускает файловую/сетевую
работу. JSON сериализует модель Pydantic; caller владеет unit of work и flush.

## Проверка перед завершением

### Локальный просмотр на macOS / OrbStack

- `scripts/maintenance/desktop_runtime.py start` запускает текущий checkout с
  существующим локальным хранилищем; API доступен только на `127.0.0.1:8000`.
  Запускайте через `.venv/bin/python`. Это не конфигурация NAS.
- Долговечные манифесты импорта Desktop находятся в
  `.operator-state/desktop-import/`; не удаляйте их как временные файлы.
- Инструкция локального запуска и границы архивного сопоставления:
  `docs/reviews/2026-09-10_desktop_import.md`.
- `desktop_runtime.py start` запускает также отдельные процессы импорта и
  расчёта времени. Это разные очереди; одного `worker.tasks` недостаточно.
  `worker.estimate_tasks` по очереди обслуживает прогноз, defect-risk ML и
  `time_calibration` и необязательный `shadow_analysis`; занятая очередь
  прогнозов не должна вытеснять остальные.
  Локальные блокировки `worker.lock` / `estimate-worker.lock` исключают повторный
  запуск процессов через этот launcher.
- `/health` — только признак живого API. Готовность локального запуска проверяется
  через `/health/ready`: SQL, текущая Alembic-схема, Redis, авторизованное чтение
  MinIO и наличие необходимых бакетов. Это `api_dependencies`, не проверка
  записи объектов/свободного места и не heartbeat работающих worker.
- Потеря NAS до получения задания или при записи ошибки не должна завершать
  цикл обработчика расчёта/ML: ограниченный backoff и повтор только на ПК владельца.
- При распаковке логов используйте пустую локальную папку; коллизии имён с учётом
  регистра и Unicode не должны перезаписывать данные на Windows/macOS. Одинаковые
  имена с разным SHA требуют решения оператора, одинаковые копии читаются один раз.
- Переносимые папки описываются `print-bundle.json`, версия 1. Корень каталога
  нельзя импортировать как одну печать. `model_reference` означает деталь внутри
  общей плиты: её ZIP относится ко всей печати. Контракт — `docs/IMPORT_BUNDLES.md`.
- Тесты на хосте запускайте с отдельной файловой SQLite БД через `DATABASE_URL`;
  контейнерное имя `postgres` из `.env` на хосте не подходит. Не запускайте
  интеграционные тесты на операторской БД.
- Тестовая очередь файлов NAS тоже должна быть отдельной временной папкой.
  `OPERATOR_INSTANCE_FILE`/write-admission также изолируются в тестовом harness;
  тесты не читают и не снимают maintenance gate рабочей установки.
  Общий pytest harness требует `APP_ENV=test` и SQLite; PostgreSQL проверяется
  отдельно миграциями, а не очисткой таблиц операторской базы тестовыми fixtures.

Минимум:

```bash
pytest -q
ruff check .
python scripts/check_migration_drift.py
```

Для затронутого модуля сначала запускайте узкие тесты. Для миграций дополнительно
проверьте upgrade на чистой SQLite БД и отсутствие нескольких Alembic heads.
